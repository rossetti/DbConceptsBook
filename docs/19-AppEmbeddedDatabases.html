Appendix G — Embedded Databases: SQLite and DuckDB

This book’s databases run on a PostgreSQL server, which programs and tools connect to over the network. An embedded database runs instead inside the program that uses it, with its data in a file. This appendix explains what an embedded database is and when you should use one, introduces two of them, SQLite, which holds the KSL’s simulation output, and DuckDB, which is built for analysis, and shows how a Kotlin program creates and queries one.

G.1 What an embedded database is

PostgreSQL is a client-server database. The server is a program of its own, always running; DataGrip, psql, and the book’s Kotlin programs are clients that connect to it, sign in as a user, and send it SQL (Appendix A). The server holds the data, enforces the constraints, and lets many clients work at once.

An embedded database has no server. Its database engine is a library that runs inside the program that opens it, and its data is an ordinary file, or a directory of files, on the program’s own disk. There is nothing to install and start, no user to create, and no password; opening the database means opening the file. When the program ends, so does the engine. The same SQL creates tables and queries them, with differences this appendix points out.

Thus, an embedded database trades the server’s services for simplicity. It cannot serve many users at once as a server does, and whoever can read the file can read the data. It needs no administration at all.

G.2 When to use one

An embedded database suits data that belongs to one program or one person.

  • A study’s own results. The quick tables of Section 12.4, written by one program and read by one analyst, need no server. The KSL writes its simulation output to an embedded SQLite database unless it is given another.
  • Data that travels with a program or a report. A file can be copied, e-mailed, or archived with the study it belongs to, and opened years later with any tool that reads its format.
  • A tool on one desktop, a test that needs a fresh database each time it runs, or a device with no network.

A client-server database suits data that is shared: many people or programs writing at once, users with different privileges (Section 9.4), data that must be backed up and kept available by someone whose job it is. HG Industries’ order and production databases are shared, which is why the book runs them on PostgreSQL. A study that starts in an embedded file and becomes shared should move to a server; the SQL mostly moves with it.

G.3 SQLite

SQLite is the most widely used embedded database. It is in the public domain, keeps a whole database in one file, and is built into phones, web browsers, and many desktop programs. Its command-line shell, sqlite3, comes with macOS and Linux and is a small download for Windows; DataGrip and DBeaver open a SQLite file directly, as a data source of type SQLite.

The companion scripts in code/sql/embedded/ build the warehouses and stock levels of stage D4 in a SQLite file. The first creates two tables, loads a few rows, and queries them. Run with sqlite3 -echo stock.db < sqlite-stock-create.sql, the shell creates stock.db if it does not exist, echoes each statement, and prints each result:

.headers on
.mode column
CREATE TABLE warehouse (
    warehouse_pk INTEGER PRIMARY KEY,
    warehouse_code TEXT NOT NULL UNIQUE,
    city TEXT NOT NULL,
    state TEXT NOT NULL
);
CREATE TABLE stock_level (
    stock_level_pk INTEGER PRIMARY KEY,
    warehouse_fk INTEGER NOT NULL REFERENCES warehouse,
    product_number TEXT NOT NULL,
    quantity_on_hand INTEGER NOT NULL
        CHECK (quantity_on_hand >= 0),
    UNIQUE (warehouse_fk, product_number)
);
INSERT INTO warehouse (warehouse_code, city, state)
VALUES ('W-FAY', 'Fayetteville', 'AR'), ('W-TUL', 'Tulsa', 'OK');
INSERT INTO stock_level
    (warehouse_fk, product_number, quantity_on_hand)
VALUES (1, 'HT-100', 120), (1, 'GC-300', 18), (2, 'HT-100', 60);
SELECT w.warehouse_code, s.product_number, s.quantity_on_hand
FROM stock_level AS s
JOIN warehouse AS w ON w.warehouse_pk = s.warehouse_fk
ORDER BY w.warehouse_code, s.product_number;
warehouse_code  product_number  quantity_on_hand
--------------  --------------  ----------------
W-FAY           GC-300                        18
W-FAY           HT-100                       120
W-TUL           HT-100                        60

The statements are the book’s own, with three changes that SQLite’s rules call for. The types are SQLite’s (TEXT for strings); a key column declared INTEGER PRIMARY KEY is numbered by SQLite itself, the role an identity column plays in PostgreSQL; and .headers and .mode are commands of the shell, not SQL, which format the output.

SQLite departs from PostgreSQL, and from the standard, in two ways that matter to a designer. The first is its types. A column’s declared type is a preference, called its type affinity, not a rule, so SQLite stores a value of another type rather than refuse it. The second script inserts the text forty into quantity_on_hand:

.headers on
.mode column
INSERT INTO stock_level
    (warehouse_fk, product_number, quantity_on_hand)
VALUES (2, 'GC-300', 'forty');
SELECT product_number, quantity_on_hand,
       typeof(quantity_on_hand) AS stored_as
FROM stock_level
WHERE warehouse_fk = 2;
product_number  quantity_on_hand  stored_as
--------------  ----------------  ---------
GC-300          forty             text
HT-100                        60  integer
CREATE TABLE stock_count (
    product_number TEXT NOT NULL,
    counted INTEGER NOT NULL
) STRICT;
INSERT INTO stock_count VALUES ('GC-300', 'forty');
Error near line 15: cannot store TEXT value in INTEGER column stock_count.counted

The insert succeeded, and typeof shows that the column now holds a text value in one row and an integer in another. Even the CHECK constraint passed, since SQLite compares any text as greater than any number. A strict table, declared with the word STRICT after its definition (SQLite 3.37 and later), enforces the declared types, and the last statement shows it refusing the same value. You should declare a SQLite table STRICT whenever its data will be analyzed, since a wrong type is otherwise stored silently.

The second departure is foreign keys. SQLite parses a REFERENCES clause but, for compatibility with old databases, enforces it only on a connection that asks, with PRAGMA foreign_keys = ON:

.headers on
.mode column
INSERT INTO stock_level
    (warehouse_fk, product_number, quantity_on_hand)
VALUES (9, 'HT-200', 5);
PRAGMA foreign_keys = ON;
INSERT INTO stock_level
    (warehouse_fk, product_number, quantity_on_hand)
VALUES (9, 'GC-400', 7);
Error near line 9: FOREIGN KEY constraint failed
SELECT stock_level_pk, warehouse_fk, product_number
FROM stock_level
WHERE warehouse_fk NOT IN (SELECT warehouse_pk FROM warehouse);
stock_level_pk  warehouse_fk  product_number
--------------  ------------  --------------
             5             9  HT-200

The first insert referred to warehouse 9, which does not exist, and SQLite accepted it: the shell’s connection had not asked. After the PRAGMA, the same kind of insert was refused. The orphan row remains, and the last query finds it with an anti-join (Section 3.7), written with NOT IN. The setting lasts only as long as the connection, so every program and tool that writes the file must turn it on; the KSL’s SQLite connections do (Section G.5).

A few other differences are worth knowing before you design for SQLite:

  • No date type. Dates and times are stored as text in the ISO form (2026-09-29 14:30:00), as numbers, or as both, and SQLite’s date functions work on any of them.
  • One writer at a time. Many connections may read at once, but a write locks the whole file briefly. That suits one program, not a busy system.
  • Limited ALTER TABLE. A table can be renamed and columns added, renamed, or dropped. Recent versions (3.53 and later; this book used 3.54) can also set or drop a column’s NOT NULL and add or drop a CHECK constraint, but a foreign key or a UNIQUE constraint still cannot be added to an existing table; the table is rebuilt instead.
  • No schemas. A file is one database with one set of tables. ATTACH opens a second file under a name, which serves where PostgreSQL would use a schema (Section 8.1).

G.4 DuckDB

DuckDB is an embedded database built for analysis. Like SQLite, it runs inside the program that opens it and keeps a database in one file, and it is open source, under the MIT license. Where SQLite is designed for a program’s many small reads and writes, DuckDB is designed for queries that scan, group, and summarize many rows. Its shell, duckdb, is a single program, installed on macOS with brew install duckdb and downloaded from duckdb.org for Windows and Linux; DataGrip and DBeaver open a DuckDB file as a data source of type DuckDB.

The difference in design lies in how the rows are stored. PostgreSQL and SQLite are row stores: each row’s values are kept together, so finding, inserting, or changing one row touches one place. DuckDB is a column store: each column’s values are kept together, so a query that averages 3 columns of a 20-column table reads only those 3, and a column of like values compresses well. Thus, a row store suits a system that records transactions one at a time, and a column store suits a study that summarizes what was recorded.

G.4.1 The stock tables in DuckDB

The companion script duckdb-stock.sql builds the tables of Section G.3 with the book’s own DDL, VARCHAR columns and all, with one change: DuckDB has no identity columns, so each key draws its values from a sequence, a named counter that nextval advances. (PostgreSQL has sequences too; an identity column is built on one.) Run in a terminal with duckdb -echo stock.duckdb < duckdb-stock.sql, it creates the tables, loads them, and queries them:

.mode column
CREATE SEQUENCE warehouse_seq;
CREATE TABLE warehouse (
    warehouse_pk INTEGER
        DEFAULT nextval('warehouse_seq') PRIMARY KEY,
    warehouse_code VARCHAR(10) NOT NULL UNIQUE,
    city VARCHAR(40) NOT NULL,
    state CHAR(2) NOT NULL
);
CREATE SEQUENCE stock_level_seq;
CREATE TABLE stock_level (
    stock_level_pk INTEGER
        DEFAULT nextval('stock_level_seq') PRIMARY KEY,
    warehouse_fk INTEGER NOT NULL REFERENCES warehouse,
    product_number VARCHAR(10) NOT NULL,
    quantity_on_hand INTEGER NOT NULL
        CHECK (quantity_on_hand >= 0),
    UNIQUE (warehouse_fk, product_number)
);
INSERT INTO warehouse (warehouse_code, city, state)
VALUES ('W-FAY', 'Fayetteville', 'AR'), ('W-TUL', 'Tulsa', 'OK');
INSERT INTO stock_level
    (warehouse_fk, product_number, quantity_on_hand)
VALUES (1, 'HT-100', 120), (1, 'GC-300', 18), (2, 'HT-100', 60);
SELECT w.warehouse_code, s.product_number, s.quantity_on_hand
FROM stock_level AS s
JOIN warehouse AS w ON w.warehouse_pk = s.warehouse_fk
ORDER BY w.warehouse_code, s.product_number;
warehouse_code  product_number  quantity_on_hand
--------------  --------------  ----------------
W-FAY           GC-300          18
W-FAY           HT-100          120
W-TUL           HT-100          60

The result is the one SQLite and PostgreSQL gave. DuckDB’s SQL is close to PostgreSQL’s, and its types are enforced. One exception is worth knowing: a length in a type, as in VARCHAR(10) or CHAR(2), is accepted and ignored, so a longer value is stored without complaint. A length rule that matters belongs in a CHECK constraint.

The rest of the script repeats SQLite’s two wrong inserts and then changes a warehouse twice:

INSERT INTO stock_level
    (warehouse_fk, product_number, quantity_on_hand)
VALUES (2, 'GC-300', 'forty');
Conversion Error: Could not convert string 'forty' to INT32

LINE 3: VALUES (2, 'GC-300', 'forty');
                             ^
INSERT INTO stock_level
    (warehouse_fk, product_number, quantity_on_hand)
VALUES (9, 'HT-200', 5);
Constraint Error: Violates foreign key constraint because key "warehouse_pk: 9" does not exist in the referenced table
UPDATE warehouse SET city = 'Springdale'
WHERE warehouse_code = 'W-FAY';
UPDATE warehouse SET warehouse_code = 'W-SPR'
WHERE warehouse_code = 'W-FAY';
Constraint Error: Violates foreign key constraint because key "warehouse_fk: 1" is still referenced by a foreign key in a different table. If this is an unexpected constraint violation, please refer to our foreign key limitations in the documentation
SELECT * FROM warehouse;
warehouse_pk  warehouse_code  city        state
------------  --------------  ----------  -----
1             W-FAY           Springdale  AR
2             W-TUL           Tulsa       OK

DuckDB refused both inserts that SQLite accepted: the text in an INTEGER column, and the stock level of a warehouse that does not exist. It accepted the change of the warehouse’s city. But it refused the change of its code, although no stock level refers to the code; the stock levels refer to warehouse_pk, which the update leaves alone. PostgreSQL would accept the update. DuckDB carries out an update of a column in a key or a UNIQUE constraint as a delete of the old row and an insert of the new one, and its foreign key sees the delete of a warehouse that stock levels still refer to. Its foreign keys have two more limits: no ON DELETE CASCADE, and one transaction cannot delete the rows that refer to a row and then the row itself. The last query shows that the refused update changed nothing.

Thus, DuckDB’s constraints suit data that is loaded and then analyzed, not data that is edited row by row. A study’s results are loaded once and queried many times, which is the work DuckDB is built for. A system of record, such as HG Industries’ orders, belongs on a server, or in SQLite when it belongs to one program.

G.4.2 Analysis straight from files

DuckDB can query a file directly: a CSV file’s name, in quotes, may stand where a table’s name would, and DuckDB reads the column names from the header and infers each column’s type from the values. The companion file code/data/frame-line-replications.csv holds three responses of every replication of the frame line’s two scenarios, long, as within_rep_view holds them (Section 12.4.2): 2 scenarios × 30 replications × 3 responses, 180 rows. The companion script duckdb-results.sql, run from the code folder with duckdb -echo < sql/embedded/duckdb-results.sql, first asks what DuckDB made of the file:

.mode column
SELECT column_name, column_type
FROM (DESCRIBE
      SELECT * FROM 'data/frame-line-replications.csv');
column_name  column_type
-----------  -----------
exp_name     VARCHAR
rep_id       BIGINT
stat_name    VARCHAR
rep_value    DOUBLE

DESCRIBE reports each column of a query’s result with its type. DuckDB read rep_id as an integer (BIGINT) and rep_value as a DOUBLE, with no CREATE TABLE and no load step. The script then summarizes the replications by scenario and response:

SELECT exp_name, stat_name, COUNT(*) AS reps,
       ROUND(AVG(rep_value), 3) AS average,
       ROUND(STDDEV_SAMP(rep_value), 3) AS std_dev
FROM 'data/frame-line-replications.csv'
GROUP BY exp_name, stat_name
ORDER BY stat_name, exp_name;
exp_name      stat_name      reps  average  std_dev
------------  -------------  ----  -------  -------
ThreeWelders  LotsCompleted  30    89.567   8.123
TwoWelders    LotsCompleted  30    89.6     8.101
ThreeWelders  TimeInShop     30    33.537   7.282
TwoWelders    TimeInShop     30    33.654   7.258
ThreeWelders  WorkInProcess  30    5.2      1.75
TwoWelders    WorkInProcess  30    5.217    1.748

Each group has 30 rows, one per replication, which accounts for all 180 rows of the file. As a check, the averages and standard deviations agree to three decimals with the across-replication statistics that the KSL computed and stored in across_rep_view (Section 12.2). The two scenarios’ averages differ by a small fraction of a standard deviation, which is why Example 12.1 compares them replication by replication.

The last statement turns the long rows of TwoWelders’ first three replications wide:

PIVOT (
    SELECT rep_id, stat_name,
           ROUND(rep_value, 3) AS rep_value
    FROM 'data/frame-line-replications.csv'
    WHERE exp_name = 'TwoWelders' AND rep_id <= 3
)
ON stat_name
USING MAX(rep_value)
ORDER BY rep_id;
rep_id  LotsCompleted  TimeInShop  WorkInProcess
------  -------------  ----------  -------------
1       85.0           28.126      3.908
2       85.0           28.981      4.094
3       86.0           36.98       5.904

PIVOT names the column whose values become columns (ON stat_name) and the aggregate that fills each cell (USING MAX(rep_value)), and the remaining column, rep_id, gives the rows. The result is Table 12.15, which Section 12.4.2 built by hand and then with one FILTER per response. Notice that PIVOT found the three columns in the data; the FILTER query listed them by hand. PIVOT is DuckDB’s own statement: neither PostgreSQL nor the SQL standard has it. DuckDB’s UNPIVOT goes the other way, and its COPY statement writes a result to a CSV file, or to a Parquet file (a column-store file format that many analysis tools read), for the next tool in a study.

G.5 Embedded databases from Kotlin and the KSL

A program opens an embedded database through JDBC, as it opens PostgreSQL (Section 10.1), with a URL that names a file instead of a server: jdbc:sqlite:stock.db or jdbc:duckdb:stock.duckdb. The driver is the engine, so the program needs only the driver’s library. The companion project’s build includes SQLite’s through the KSL.

The KSL wraps SQLite in classes of its ksl.utilities.io.dbutil package that Section 10.4 introduced: SQLiteDb creates or opens a database in a directory, and the function Database.createSimpleDb creates one with tables defined by DbTableData data classes, the quick tables of Section 12.4. The KSL also supports Apache Derby, an embedded database written in Java, through DerbyDb; its developers retired Derby in October 2025, so use it only to open a database that already uses it. A KSLDatabase created with only a name, KSLDatabase("study.db"), is an embedded SQLite database that holds the KSL’s simulation output. The KSL’s SQLite connections turn on foreign key enforcement, so the problem of the previous section does not arise in them.

The companion program SolverRunsSQLite.kt writes the solver runs of Section 12.4 to a SQLite file and summarizes them. It creates the database and its table from the data class SolverRun:

val dir = Files.createDirectories(Path.of("build", "embedded"))
val db = Database.createSimpleDb(
    tableDefinitions = setOf(SolverRun()),
    dbName = "solver-runs.db",
    dbDirectory = dir
)

It then inserts four runs, as objects of the data class:

val runs = listOf(
    SolverRun(1, "Rosenbrock", "SA-slow", 1, 10.05, 900, 0.005),
    SolverRun(2, "Rosenbrock", "SA-slow", 2, 10.30, 1000, 0.030),
    SolverRun(3, "Rosenbrock", "RS", 1, 10.20, 1000, 0.020),
    SolverRun(4, "Rosenbrock", "RS", 2, 10.90, 1000, 0.090)
)
val inserted = db.insertAllDbDataIntoTable(runs, "solver_run")
println("Inserted $inserted rows into solver_run")

and summarizes them by solver with a grouping query:

val sql = """
    SELECT solverLabel, COUNT(*) AS runs,
           ROUND(AVG(gap), 3) AS average_gap
    FROM solver_run
    GROUP BY solverLabel
    ORDER BY solverLabel
    """.trimIndent()
db.fetchCachedRowSet(sql)?.let { rs ->
    while (rs.next()) {
        println("%-8s %d  %.3f".format(rs.getString(1), rs.getInt(2), rs.getDouble(3)))
    }
}

It prints:

Inserted 4 rows into solver_run
RS       2  0.055
SA-slow  2  0.017

The table is the one whose CREATE TABLE statement Section 12.4 printed, with its DOUBLE columns; SQLite accepts that type, where PostgreSQL refused it. The file build/embedded/solver-runs.db can be opened in DataGrip or with sqlite3 and queried like any other database, and it can be copied, with the study it belongs to, to anyone.

The KSL does not include DuckDB. A program that writes to DuckDB adds its driver, org.duckdb:duckdb_jdbc, to the build; the driver carries DuckDB’s engine compiled for each operating system, and is some 85 MB. A study more often needs DuckDB only for analysis, and then needs no program of its own: every KSL database can write its views as CSV files, one per view, with the function exportAllViewsAsCSV, and DuckDB queries those files as Section G.4 queried frame-line-replications.csv.

G.6 Choosing a database

Table G.1 sets the three databases side by side on the matters this appendix has raised.

Choose PostgreSQL, or another server, for data that is shared. Choose SQLite for data that belongs to one program, one study, or one person, and declare its tables STRICT and its connections’ foreign keys on. Choose DuckDB to analyze data that has already been recorded, a study’s results or a set of exported files, where its column storage and its SQL make the summaries quick to write and to run.

G.7 Exercises

Exercise G.1 For each situation, say whether an embedded database or a database server suits it, and why.

  1. A simulation study run by one engineer, whose results are archived with the final report.
  2. HG Industries’ order entry, used by six people in two warehouses.
  3. A tablet application that inspectors carry onto the plant floor, which records measurements while out of network range and sends them later.
  4. A benchmark of optimization solvers run by three students on their own laptops, whose results must be combined for one analysis.

Exercise G.2 Using the SQLite scripts of Section G.3:

  1. Rewrite the stock_level table of sqlite-stock-create.sql as a strict table, and say which of the inserts of sqlite-stock-affinity.sql it would refuse.
  2. The CHECK (quantity_on_hand >= 0) of the original table accepted the text forty. Write a check that refuses any value that is not an integer, for a table that is not strict, using SQLite’s typeof function.

Exercise G.3 A colleague’s SQLite file of stock levels was written for months by a program that never turned on foreign keys.

  1. Write a query that finds every stock level whose warehouse does not exist.
  2. Why does turning the setting on now not find or remove those rows?
  3. What should every program that writes the file do from now on?

Exercise G.4 The same CREATE TABLE warehouse (...) statement is run in PostgreSQL, SQLite, and DuckDB.

  1. Under what name does each database store the table?
  2. A query copied from a database that folds unquoted names to upper case, as the SQL standard specifies, names the table "WAREHOUSE", in double quotes. Does it work in PostgreSQL? In SQLite and DuckDB? Explain.

Exercise G.5 The script duckdb-stock.sql of Section G.4 changed warehouse W-FAY’s city, and DuckDB refused to change its code.

  1. Which column do the stock levels refer to, and did the refused update change it?
  2. Why did DuckDB refuse the update, when PostgreSQL would accept it?
  3. A colleague proposes keeping HG Industries’ order entry in a DuckDB file, since DuckDB’s SQL is so close to PostgreSQL’s. Name two operations of order entry that the limits of Section G.4 would make fail or need a workaround, and recommend where the orders should be kept instead.

Exercise G.6 Using DuckDB and the file code/data/frame-line-replications.csv of Section G.4, run from the code folder:

  1. Write a query that returns, for each scenario, the replication with the longest time in shop: the scenario, the replication, and the time in shop rounded to three decimals. Explain what you notice about the two rows.
  2. Repeat the Little’s law check of Table 12.17 for the first five replications of TwoWelders, building the wide table with PIVOT instead of FILTER. Does your result match Table 12.17?

Exercise G.7 Run SolverRunsSQLite.kt of Section G.5, and open the file it writes in DataGrip, DBeaver, or sqlite3.

  1. Write a query that returns, for each solver, the run with the smallest gap: the solver, the replication, and the gap.
  2. Add a fifth run of your own with a gap of NULL. What does the program’s summary query now report for its solver, and why?
