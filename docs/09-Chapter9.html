9  Views, Transactions, and Concurrency

NoteLearning objectives

After reading this chapter you should be able to:

  • define a view, use it in queries, and say when a view can be updated
  • group statements into a transaction with BEGIN, COMMIT, and ROLLBACK, and explain the ACID properties
  • recognize the lost update and the read anomalies of concurrent transactions, and choose an isolation level that prevents them
  • grant and revoke privileges on tables and views

The chapters so far have treated a database as if one person used it at a time, and as if every statement stood alone. Neither is true in a working plant. Sales, shipping, and quality use the same tables at once, and a single piece of work, such as shipping an order, takes several statements that make sense only together. This chapter presents the database’s answers: views, which give each user the queries they need under a name; transactions, which make several statements succeed or fail as one; isolation, which keeps concurrent users from spoiling each other’s work; and privileges, which decide who may do what.

The chapter is brief, and it shows each idea once, mostly on HG Industries’ distribution schema at stages D3 to D5, and for privileges on the production schema of stage P1. The ideas matter to an engineer less as theory than as explanations: of why a report run twice gives two answers, why a statement waits, and why a program must sometimes try a change again.

TipFollowing along

Several results in this chapter come from a schedule: a sequence of statements run by two sessions, A and B, in the order the table shows, as two clerks at two terminals would run them. Each schedule runs against a copy of the book’s database that is discarded afterward. To keep the statements short, a schedule names tables without their schema, as a session whose search path lists distribution may (Section 8.1). To try one yourself, open two query consoles in DataGrip or DBeaver, leave both in auto-commit, as in the earlier chapters, and run the statements in order, typing BEGIN, COMMIT, and ROLLBACK where the schedule shows them (Section 9.2).

9.1 Views

This section presents views: queries that the database keeps under a name.

A view is a named query stored in the database, which can be used in other queries as if it were a table. It stores no rows. Each time a query uses the view, the database runs the view’s query and uses its result, so a view always reflects the tables as they are at that moment. Recall the flat order report of Section 7.2: normalization split it into four tables, and Section 7.6 observed that the report itself belongs in a query. A view gives that query a name:

CREATE VIEW distribution.order_report AS
SELECT o.order_number, c.customer_number,
       c.name AS customer_name, l.line_number,
       p.product_number, p.description, l.quantity
FROM distribution.customer_order AS o
JOIN distribution.customer AS c
  ON c.customer_pk = o.customer_fk
JOIN distribution.order_line AS l
  ON l.customer_order_fk = o.customer_order_pk
JOIN distribution.product AS p
  ON p.product_pk = l.product_fk;

The view is queried as a table is. A user who wants the lines of SO-5004 no longer writes the joins:

Because the view stores no rows, the anomalies of Section 7.2 cannot arise in it. A change to a product’s description is made once, in product, and every row of the report shows it at once:

UPDATE distribution.product
SET description = 'Two-wheel steel hand truck'
WHERE product_number = 'HT-100';

Both HT-100 lines of Table 9.2 show the new description, from the one row that changed. A view serves three purposes. It simplifies: a join or a calculation written once is used by name. It insulates: if the tables behind it are later split or renamed, the view can be redefined so that the queries built on it keep working. And it restricts: a user can be allowed to query a view without being allowed to query the tables behind it, which Section 9.4 takes up. A view that answers a standing question of the business is worth its name. For example, the warehouse manager’s question “what needs reordering?” becomes, at stage D4:

CREATE VIEW distribution.stock_to_reorder AS
SELECT w.warehouse_code, p.product_number,
       s.quantity_on_hand, s.reorder_point
FROM distribution.stock_level AS s
JOIN distribution.warehouse AS w
  ON w.warehouse_pk = s.warehouse_fk
JOIN distribution.product AS p
  ON p.product_pk = s.product_fk
WHERE s.quantity_on_hand < s.reorder_point;

Can a view be changed, as a table can? A view is updatable when each of its rows comes from one row of one table, so that the database knows which row an INSERT, UPDATE, or DELETE on the view must change. In PostgreSQL, a view is updatable automatically when it selects from a single table and has none of DISTINCT, GROUP BY, HAVING, aggregates, window functions, LIMIT or OFFSET, a WITH clause, or set operations such as UNION. Even then, only the view’s columns that are plain columns of the table can be changed through it. The order report joins four tables, and is not updatable:

DELETE FROM distribution.order_report
WHERE order_number = 'SO-5004';
ERROR:  cannot delete from view "order_report"
DETAIL:  Views that do not select from a single table or view are not automatically updatable.
HINT:  To enable deleting from the view, provide an INSTEAD OF DELETE trigger or an unconditional ON DELETE DO INSTEAD rule.

A single-table view is updatable, and it raises a question of its own. The view below shows the customers in Oklahoma, and a clerk who works only with that territory could add customers through it. Nothing yet stops the clerk from adding, through the view, a customer in Arkansas, a row the view itself would never show. The clause WITH CHECK OPTION makes the view refuse such a row:

CREATE VIEW distribution.oklahoma_customer AS
SELECT customer_number, name, city, state
FROM distribution.customer
WHERE state = 'OK'
WITH CHECK OPTION;
INSERT INTO distribution.oklahoma_customer
    (customer_number, name, city, state)
VALUES ('C-1009', 'Rogers Farm Supply', 'Rogers', 'AR');
ERROR:  new row violates check option for view "oklahoma_customer"
DETAIL:  Failing row contains (9, C-1009, Rogers Farm Supply, Rogers, AR).

A view stores no rows: its query runs, as part of the query that uses it, every time it is used, which is what keeps it current. A query of a view therefore costs about what the same query would cost written out with the view’s joins: PostgreSQL merges the view’s query into the query that uses it, so that a condition such as order_number = 'SO-5004' is applied inside the joins. PostgreSQL also offers a materialized view, which stores its result and is brought up to date only when told to (REFRESH MATERIALIZED VIEW); it trades currency for speed, as the summary tables of Chapter 11 do. The next section turns from naming queries to grouping changes.

9.2 Transactions and the ACID properties

This section presents transactions: groups of statements that succeed or fail as one.

Shipping an order at HG Industries is several changes. The clerk records a shipment, a shipment line for each order line shipped, and a smaller quantity on hand for each product that left the warehouse. For order SO-5011 at stage D5, 30 HT-100 hand trucks and 12 GC-300 carts leaving Fayetteville, the changes are four statements; the stock levels of the two products in Fayetteville have keys 1 and 3 (stock_level_pk), and the order’s lines have keys 19 and 20 (order_line_pk):

INSERT INTO distribution.shipment
    (shipment_number, shipped_on, carrier,
     customer_order_fk, warehouse_fk)
VALUES ('SH-9012', DATE '2026-03-10',
        'Boston Mountain Freight', 11, 1);

INSERT INTO distribution.shipment_line
    (shipment_fk, order_line_fk, quantity)
SELECT shipment_pk, 19, 30 FROM distribution.shipment
WHERE shipment_number = 'SH-9012'
UNION ALL
SELECT shipment_pk, 20, 12 FROM distribution.shipment
WHERE shipment_number = 'SH-9012';

UPDATE distribution.stock_level
SET quantity_on_hand = quantity_on_hand - 30
WHERE stock_level_pk = 1;

UPDATE distribution.stock_level
SET quantity_on_hand = quantity_on_hand - 12
WHERE stock_level_pk = 3;

The four statements belong together. A shipment recorded without its stock decrease overstates the stock; a stock decrease without its shipment loses carts from the books. Suppose that the clerk, not noticing that SO-5011 has already shipped, runs the four statements again, as shipment SH-9013. The warehouse had 18 GC-300 carts and now has 6, so the last statement drives the quantity below zero, and the check of stock_level refuses it. Run one at a time, as the tools run statements by default, the first three have already taken effect:

The database of Table 9.4 now contradicts itself. It records two shipments of SO-5011, and a second 30 hand trucks gone from Fayetteville (90 became 60), but the 12 carts of the second shipment never left the stock (6 remain). Someone must find and repair the damage by hand.

A transaction is a sequence of statements that the database treats as one unit: either every change it makes takes effect, or none does. BEGIN (or the standard START TRANSACTION) opens a transaction; COMMIT ends it and makes its changes permanent; ROLLBACK ends it and discards them. In PostgreSQL, a statement that fails inside a transaction makes the whole transaction fail: the database refuses every later statement until the transaction ends, and a COMMIT then rolls it back. (The SQL standard, and several other systems, undo only the failed statement and let the transaction go on.) The same mistake, made inside a transaction, leaves no trace:

Read Table 9.5 step by step. The first three changes succeed, as before, but inside the transaction. The fourth is refused, and from then on the transaction has failed: even the harmless count of step 6 is refused, and the COMMIT of step 7 rolls everything back. Afterward SO-5011 has one shipment, and the stock stands at 90 and 6, as the first shipment left it. The database is as it was before the clerk’s mistake, and the clerk has an error message to act on.

An error typed in a console has the same effect on an open transaction. Until you type ROLLBACK (or COMMIT, which then rolls back), PostgreSQL refuses every statement with the message that the current transaction is aborted. The ROLLBACK undoes all of the transaction’s work, not only the failed statement, and with it any setting made by SET inside the transaction, such as a search path or a role (Section 9.4). When a statement may fail and the work before it should survive, mark the point before it with a savepoint. Suppose that, after the first shipment of SO-5011, a clerk ships 30 more hand trucks from Fayetteville for another order, and 12 carts with them if the stock allows:

BEGIN;
UPDATE distribution.stock_level
SET quantity_on_hand = quantity_on_hand - 30
WHERE stock_level_pk = 1;
SAVEPOINT before_carts;
UPDATE distribution.stock_level
SET quantity_on_hand = quantity_on_hand - 12
WHERE stock_level_pk = 3;
ROLLBACK TO SAVEPOINT before_carts;

The second UPDATE is refused, since only 6 carts remain, and ROLLBACK TO SAVEPOINT before_carts undoes it alone. The transaction is usable again, with the hand trucks’ decrease still in it. The clerk can ship the 6 carts that remain and commit, or end with ROLLBACK and undo everything.

The guarantees a transaction gives are summarized by four properties, known by their initials as ACID:

  • Atomicity: the transaction’s changes take effect all together or not at all, as Table 9.5 showed.
  • Consistency: a transaction takes the database from a state that satisfies every rule to another that does: the constraints the database declares, and the business’s rules that the transaction’s statements carry out together. Each statement is checked against the declared constraints as it runs, and a transaction that cannot finish consistent is rolled back.
  • Isolation: transactions running at the same time do not see each other’s unfinished changes, and do not spoil each other’s work, to the degree the isolation level promises (Section 9.3).
  • Durability: once COMMIT returns, the changes survive a crash of the server or of the machine.

The first three properties can be seen in a schedule. Durability is the one you trust: PostgreSQL writes every change first to a write-ahead log, a file of changes in the order they were made, and, under its default settings, does not report a commit until the log records it, so that after a crash it can replay the log and recover every committed transaction. Durability does not protect against a mistaken DELETE that was committed, a failed disk, or a lost machine. For those you need a backup, a copy of the database made on purpose and kept elsewhere. PostgreSQL’s pg_dump program writes a database to a single file, and pg_restore (or psql, for a plain SQL dump) rebuilds it, into a new database if need be; a backup that has never been restored should not be trusted.

A transaction also changes when some constraints are checked. Recall from Section 2.3 that PostgreSQL’s NO ACTION and RESTRICT both refuse a deletion that would leave a foreign key pointing nowhere. The SQL standard has RESTRICT check at once and NO ACTION at the end of the statement. In PostgreSQL the difference that matters is another. A NO ACTION foreign key can be declared DEFERRABLE INITIALLY DEFERRED, and its check then waits until COMMIT, which lets a transaction pass through an inconsistent state on its way to a consistent one. A RESTRICT check is never deferred.

Two practical points follow. First, DataGrip and DBeaver run each statement in its own transaction, committed at once (auto-commit). Both tools can switch a console to manual transactions, but this book keeps the consoles in auto-commit and types BEGIN where it wants a transaction. A DELETE typed in a console is therefore permanent the moment it runs; to experiment safely, type BEGIN first, and end with ROLLBACK. Second, the three inserts that recorded a new customer’s order in Example 8.2 belong in one transaction, between BEGIN and COMMIT, for the reason this section has shown. The next section considers transactions that run at the same time.

9.3 Concurrency and isolation levels

This section considers transactions that run at the same time, and the isolation that keeps them from spoiling each other’s work.

A database serves many sessions at once, and their transactions interleave: one clerk’s statements run between another’s. Most of the time they touch different rows and nothing goes wrong. Trouble comes when two transactions read and change the same rows, and the classic case is the lost update: two transactions read a value, each computes a new value from what it read, and the second to write overwrites the first, whose change is lost.

At stage D5 the Fayetteville warehouse holds 18 GC-300 carts (stock level 3). Clerk A ships the 12 carts of SO-5011, and at the same moment clerk B ships 10 carts for another order. Each reads the quantity on hand, subtracts, and writes the result back:

Both clerks read 18 (steps 3 and 4). Clerk A writes 6, which is 18 − 12. Clerk B’s write must wait (step 6), because A’s uncommitted change locks the row; when A commits, B’s write goes ahead and sets 8, which is 18 − 10. The books now say 8 carts remain, after 22 carts were shipped from 18. A’s update is lost, and nothing refused anything: each statement was legal on its own.

Notice step 6. A transaction that changes a row holds a lock on it until the transaction ends, and another transaction that wants to change the same row waits. The lock did not prevent the lost update, because B’s mistake was made earlier, when it read 18 and decided on 8. The repair is to let the database do the arithmetic, in a single statement that reads and writes the row while holding its lock, and to state the condition under which the change is allowed:

B’s update waits for A’s lock, as before (step 4), and when A commits it reads the row again, as A left it: 6 carts, fewer than 10, so its condition fails and it updates no row (step 6). Clerk B’s program learns that the stock is short, rolls back, and can offer a partial shipment or a backorder. The stock ends at 6, which is right. When a program must read a value and decide before it writes, as when it shows the quantity to a clerk, it can take the lock at the read with SELECT ... FOR UPDATE; a second transaction’s SELECT ... FOR UPDATE of the same row then waits until the first ends.

The lost update is one of several ways concurrent transactions can interfere. The SQL standard names three more, which concern what a transaction reads:

  • A dirty read reads a change that another transaction has made but not committed, and may yet roll back.
  • A nonrepeatable read reads a row twice and gets two values, because another transaction changed and committed the row in between.
  • A phantom read runs the same query twice and finds rows the second time that were not there the first, because another transaction inserted them.

One more interference involves no row that both transactions change. In a write skew, two transactions read the same rows, and each then changes a different row on the strength of what it read, so that the two changes together break a rule that each alone keeps. Table 9.11 shows one.

The isolation level of a transaction says which of these it is protected from. The standard defines four levels, and Table 9.8 gives what each allows, with PostgreSQL’s behavior where it is stricter than the standard requires.

PostgreSQL’s default, and that of most systems, is READ COMMITTED: each statement sees the data as committed when the statement began. It is a sensible default for short transactions, and it allows the nonrepeatable read. Suppose that the production planner runs a report inside one transaction, totaling the GC-300 carts in both warehouses, while a shipment commits:

The planner’s two totals disagree, 58 and then 46, within one transaction. A report whose parts are computed by several queries, a total on one page and a breakdown on the next, can then fail to add up. Under REPEATABLE READ, the transaction sees the database as it was when its first statement ran, and every query in it sees the same data. The price is that such a transaction cannot change a row that another transaction changed after its first statement ran; it fails instead, and must be tried again:

In Table 9.10, A’s total is 58 both times (steps 2 and 4), although B’s shipment has committed in between. When A then ships SO-5012’s 4 carts from the same row, PostgreSQL refuses (step 5): A would be changing a row it has not seen in its current form. A tries again in a new transaction, which sees B’s change, and the stock ends at 18 − 12 − 4 = 2. A program that uses REPEATABLE READ or SERIALIZABLE must be written to retry a transaction that fails this way.

REPEATABLE READ refuses a change to a row that another transaction changed first. It does not stop two transactions that change different rows on the strength of what both read. Suppose that HG Industries keeps at least 30 GC-300 carts across its two warehouses: 18 in Fayetteville (stock level 3) and 40 in Tulsa (stock level 7). Two planners each check the total, 58, and each takes carts for a rush order. Planner A takes the 18 in Fayetteville, which leaves 40; planner B takes 25 in Tulsa, which leaves 33. Each change keeps the rule, and the two together do not:

Both planners read 58 (steps 3 and 4), both changes succeed, and both transactions commit. The total is now 15, half of the 30 the rule requires. Neither transaction changed a row that the other changed, so REPEATABLE READ found nothing to refuse. This is a write skew, and preventing it is what SERIALIZABLE adds. At SERIALIZABLE, PostgreSQL also keeps track of what each transaction has read, and refuses a transaction whose commit would give a result that no order of running the transactions one at a time could give. The same schedule at SERIALIZABLE:

In Table 9.12, planner A commits (step 7), and planner B’s COMMIT fails (step 8): run after A’s, B’s transaction would have read 40, not 58. The total stays at 40. Planner B’s program tries again, reads 40, and finds that taking 25 would break the rule. The price is the one REPEATABLE READ charges, a transaction that fails and must be retried, and PostgreSQL may refuse, to be safe, a transaction that would have done no harm. Thus, SERIALIZABLE is the level for a transaction that checks a rule spanning several rows before it changes one of them.

Two more facts complete the picture. First, PostgreSQL keeps several versions of a changed row, so that a reader sees the version its snapshot calls for; as a result, an ordinary read never waits for a write, and a write never waits for an ordinary read. A read that locks, such as SELECT ... FOR UPDATE, can wait. Two transactions that change the same row wait for each other, as B did in Table 9.6, and so do two that insert the same value of a UNIQUE column: the second waits until the first ends, then fails if the first committed and goes ahead if it rolled back. Second, two transactions can wait for each other at once: A has changed row 1 and wants row 3, while B has changed row 3 and wants row 1. Neither can proceed, a situation called a deadlock. PostgreSQL detects it after a second or so and cancels one transaction with an error, which the program must retry. Programs that change several rows avoid most deadlocks by changing them in the same order, for example by key.

For an engineer who writes reports and programs against a shared database, three habits follow. Keep transactions short, since a transaction holds its locks until it ends. Let the database compute changes (SET q = q - 12) rather than writing back values computed elsewhere. And run a report that must add up within one transaction at REPEATABLE READ, and a transaction that checks a rule across several rows before it changes one at SERIALIZABLE. The next section turns from sessions that interfere by accident to users who are kept apart on purpose.

9.4 Security and privileges

This section presents how a database decides who may read and change what.

Every session connects to PostgreSQL as a role, a name that the database knows and grants privileges to. A role may be a person, a program, or a group: a role that can log in is a user, and a role granted to other roles is a group, whose privileges its members share. A privilege is permission to perform one kind of operation on one object: SELECT, INSERT, UPDATE, or DELETE on a table or view, and USAGE on a schema, which is needed to reach the tables in it at all. GRANT gives privileges, and REVOKE takes them back. A new role has none, apart from what is granted to everyone.

Privileges follow the jobs. A sales clerk at HG Industries reads customers and products, and records orders and their lines; the clerk has no reason to delete an order or to change a product. The statements below create a group role for the sales department and grant it those privileges and no others:

CREATE ROLE hg_sales NOLOGIN;
GRANT USAGE ON SCHEMA distribution TO hg_sales;
GRANT SELECT ON distribution.customer,
                distribution.product TO hg_sales;
GRANT SELECT, INSERT ON distribution.customer_order,
                        distribution.order_line TO hg_sales;

NOLOGIN makes hg_sales a group: nobody logs in as it. Each clerk is a login role of their own, CREATE ROLE ... LOGIN PASSWORD ..., made a member of the group with GRANT hg_sales TO the clerk, so that the privileges are managed in one place and each session still identifies the clerk who opened it. A session can take on a role it belongs to with SET ROLE. Acting as hg_sales, a query of the orders succeeds:

SET ROLE hg_sales;

A deletion, which the role was not granted, is refused:

DELETE FROM distribution.customer_order
WHERE order_number = 'SO-5012';
ERROR:  permission denied for table customer_order

A privilege can be narrower than a table. The production department’s part table holds each part’s standard cost, which sales should not see. Privileges can be granted on some columns only, as in GRANT SELECT (part_number, description) ON production.part TO hg_sales; or a view can show the columns sales needs, and sales can be granted the view but not the table. A view is checked with the privileges of its owner, so a user who may read the view reads the table’s rows through it without any privilege on the table. The query below, cut to the first four parts, runs as hg_sales; the one after it, which asks the table for costs, is refused:

CREATE VIEW production.part_catalog AS
SELECT part_number, description, unit_of_measure
FROM production.part;

GRANT USAGE ON SCHEMA production TO hg_sales;
GRANT SELECT ON production.part_catalog TO hg_sales;
SELECT part_number, standard_cost
FROM production.part;
ERROR:  permission denied for table part

PostgreSQL can go further, and restrict the rows a role may see or change with row-level security, so that, say, each warehouse’s clerks see only their warehouse’s stock. This book does not use it.

The same care applies to programs. A program that reads the database for a report should connect as a role that may only read; a program that records inspections, as Chapter 10 will write, as a role that may insert inspections and measurements and nothing more. No program should connect as the database’s owner or as a superuser, and no password belongs in a script or in code kept under version control: the book’s companion code reads its password from db.properties, a file that is never committed.

9.5 Summary

A view is a named query, and it is always current. It stores no rows; each use runs its query against the tables as they are. Views simplify queries, insulate them from changes to the tables, and restrict what a user sees. A simple view over one table, without grouping, DISTINCT, LIMIT, window functions, or set operations, can be updated, and WITH CHECK OPTION refuses a change the view could not show.

A transaction makes several statements succeed or fail as one. BEGIN opens it, COMMIT makes its changes permanent, and ROLLBACK discards them. In PostgreSQL a failed statement fails the whole transaction, and only ROLLBACK, or ROLLBACK TO SAVEPOINT, lets work go on. Its guarantees are atomicity, consistency, isolation, and durability, and durability is not a backup.

Concurrent transactions can spoil each other’s work, and isolation limits the damage. Two transactions that read a value, compute, and write it back lose an update; letting the database compute the change, under a condition, prevents it. The isolation level decides which read anomalies a transaction can meet: READ COMMITTED, the default, allows nonrepeatable reads, and REPEATABLE READ prevents them at the price of transactions that fail and must be retried. SERIALIZABLE also prevents write skew, two transactions that each change a different row on the strength of what both read.

Privileges decide who may do what. A role is a user or a group; GRANT and REVOKE give and take privileges on schemas, tables, views, and columns. Grant each role only what its job needs, and use a view to show some columns or rows of a table without granting the table.
