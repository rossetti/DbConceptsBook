Appendix B — Kotlin and KSL Setup

Most of this book needs only PostgreSQL and a database tool (Appendix A). Two chapters also run programs: Chapter 10, which connects Kotlin programs to the database, and Chapter 12, which reads a simulation model’s inputs from the database and analyzes its results. Their programs are written in Kotlin and use the Kotlin Simulation Library, the KSL, whose database utilities wrap JDBC (Rossetti 2025). This appendix sets up what those programs need: a Java Development Kit, an editor, the companion code project, and its connection to your database.

B.1 Installing a JDK and IntelliJ IDEA

Kotlin programs run on the Java Virtual Machine, so they need a Java Development Kit (JDK). The companion project asks for version 21, the version the KSL is built for, and you need not install it yourself: the project’s build is configured to download a JDK 21 the first time it runs on a machine that has none. If you prefer to install one, any JDK 21 distribution works, such as Eclipse Temurin from adoptium.net.

The book uses IntelliJ IDEA, JetBrains’ editor for Kotlin and Java, from jetbrains.com/idea. Since release 2025.3 it is one download whose free features include everything the companion code needs; a subscription adds features the book does not use. IntelliJ IDEA can also download a JDK for you, from File, Project Structure, SDKs.

If you use the KSL in a simulation course, you may already have both. The KSL’s own textbook has an appendix on the same setup (Rossetti 2025), and the companion project here is an ordinary Gradle project like its examples.

B.2 Opening the companion code project

The companion code is the public repository https://github.com/rossetti/DbConceptsBookCode. Download it from there (Code, then Download ZIP) and unzip it, or clone it with Git. The book calls the folder that holds it, the one that contains build.gradle.kts, the code folder. It holds the SQL scripts the chapters refer to and the Kotlin programs, and it is a Gradle project: build.gradle.kts declares what the programs depend on, the KSL among them, and the Gradle wrapper (gradlew, or gradlew.bat on Windows) downloads Gradle and those dependencies the first time the project is built.

To open it, start IntelliJ IDEA, choose File, Open, and select the code folder, the one that contains build.gradle.kts. IntelliJ IDEA recognizes the Gradle project and imports it, downloading the dependencies from Maven Central; the first import takes a few minutes, and later ones seconds. The project’s README.md describes its layout. The programs are under src/main/kotlin/dbconcepts/, one package for each subject: connecting for the connection itself, programming for the programs of Chapter 10, and simulation for those of Chapter 12.

B.3 Configuring the database connection

The programs read their connection settings from a file, db.properties, in the code folder, so that no password is written into a program (Section 10.2 explains why that matters). The project provides a template, db.properties.example; copy it to db.properties and fill it in:

host=localhost
port=5432
database=dbconcepts
user=postgres
password=

Give the user and password you connect with in DataGrip or DBeaver (Section A.1): with Postgres.app, your login name and an empty password; with the Windows installer, postgres and the password you chose. The database is dbconcepts, created and loaded as Section A.5 describes. The programs of Chapter 10 expect it loaded through stage Q; load code/sql/load/through-q.sql (or any later stage) before running them.

Keep db.properties to yourself. It holds a password, so it is excluded from the project’s version control, and you should not e-mail it or copy it into a report. Every program opens the database the same way, through the object BookDatabase in the connecting package, which reads the file.

B.4 Running your first program

The first program to run is CheckConnection.kt, in the connecting package. It connects with your settings, asks the server for its version, and lists the tables of each of the book’s schemas:

val rs = db.fetchCachedRowSet("SELECT current_setting('server_version')")
if (rs != null && rs.next()) {
    println("Connected to PostgreSQL ${rs.getString(1)}")
} else {
    println("Could not query the server. Check the settings in db.properties.")
    return
}
for (schema in listOf("distribution", "production", "quality")) {
    val tables = db.tableNames(schema).sorted()
    if (tables.isEmpty()) {
        println("$schema: (not loaded)")
    } else {
        println("$schema:")
        tables.chunked(4).forEach { println("    " + it.joinToString(", ")) }
    }
}

In IntelliJ IDEA, open the file and click the green arrow beside fun main(). From a terminal in the code folder, the Gradle wrapper runs it:

./gradlew run

In the Windows Command Prompt, the command is gradlew run. With the database loaded through stage Q, it prints:

Connected to PostgreSQL 18.6 (Postgres.app)
distribution:
    customer, customer_order, order_line, product
    shipment, shipment_line, stock_level, warehouse
production:
    bom_line, certification, machine, manufactured_part
    operation, operator, part, purchased_part
    work_center, work_order
quality:
    characteristic, defect_count, defect_type, inspection
    measurement

The first line gives your server’s version, which may differ from the book’s; the words in parentheses appear only with Postgres.app. If the program stops instead, its message says why. No connection settings means db.properties is missing from the code folder. A failed password means the user or password in the file is not the one the server expects. A refused connection means the server is not running, or is not at the host and port in the file. A database that does not exist means dbconcepts has not been created yet. A schema reported as (not loaded) means the database exists but the load file has not been run.

Every other program runs the same way: from IntelliJ IDEA, with the green arrow beside its main, or from a terminal by naming its class, the file’s name followed by Kt:

./gradlew run -PmainClass=dbconcepts.programming.LotMeasurementsKt

The simulation of Section 12.1, RunFrameLine.kt in the simulation package, writes the KSL’s output schema, ksl_db, into the database it connects to. Run on dbconcepts loaded through stage Q, it reproduces stage K of Section 12.2, with the same statistics, since the model’s random number streams are fixed. The KSL also writes its reports and any files a program creates under kslOutput in the code folder.
