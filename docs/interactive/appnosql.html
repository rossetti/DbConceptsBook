Why NoSQL Databases Exist and the Four Families

Read the sections

Self-Check

1. Why does a key-value store often sit in front of another database?

Yes. Its speed comes from its simplicity: it stores a value under a key and does not look inside it.

A key-value store checks nothing; it does not even look inside the values it holds.

It finds a record by its key and nothing else. Questions about the values need another database.

A key-value store holds a value per key. Keeping years of history is the work of a historian or a warehouse.

2. Which question can a document database answer that a key-value store cannot?

Both can do that. Finding a record by its key is all a key-value store does.

Yes. A document database looks inside its documents and can search by the values of their fields. A key-value store does not look inside the value it holds.

Both find a record by its key. Speed at that is the key-value store’s strength, not a question only the document database can answer.

Spreading data over many machines is one of the needs behind NoSQL in general, not a difference between these two families.

3. True or False: a plant historian holds an oven’s temperatures along with the plant’s lots and work orders, so a question such as “the temperatures during the runs of one lot that failed inspection” is answered inside the historian.

A historian holds tags measured over time. It does not hold orders, parts, or work orders.

Correct. The usual design summarizes the readings, such as each tag’s average, minimum, and maximum over each hour or run, and loads the summaries into a relational database, where they join the rest of the plant’s data.

The Trade-offs

Read the section

Self-Check

1. A document database applies schema on read. What is its main cost?

That would be schema on write. A document database usually stores whatever document it is given.

Yes. The program decides what the fields mean, so a misspelled field is accepted when written and can make a later query answer wrongly.

That is the cost schema on read avoids: the structure can change without a redesign.

A document database can search by the values of fields. The trouble is that nothing guarantees which fields are there.

2. True or False: a document database can never check the fields of the documents it stores, since schema on read is all it offers.

Many document databases now let a designer declare rules that documents must obey.

Correct. Declared rules move a document database part of the way back to schema on write. Without them, it stores whatever document it is given.

3. A NoSQL database keeps several copies of each record and offers eventual consistency. For which use is a read from a copy that has not yet received the latest change most likely to do harm?

A value a second old does no harm on a dashboard.

Yes. Each planner may allocate from a value the other has already used. Many NoSQL databases let a program ask for stronger consistency on the operations that need it, at the cost of speed.

Readings that never change are read back the same from any copy once they have arrived.

Last year’s figures are no longer changing, so a short delay between copies does not matter to them.

Documents in PostgreSQL

Read the section

Self-Check

1. The query of January’s orders filters with WHERE document ->> 'order_date' < '2026-02-01'. Why does the comparison give the right orders?

Yes. The comparison is of text, and it works only because of the form the dates were written in.

->> always returns text. Nothing in the document declares the field a date.

PostgreSQL compares two strings as text. The form of these dates makes text order and date order agree.

Dates written in another form, such as month first, need not sort as text in date order.

2. The condition document @> '{"lines": [{"product_number": "GC-300"}]}' is applied to each order document. Which documents does it keep?

Yes. @> asks whether a document contains another, and a line with more fields still contains the one field asked for.

Containment does not require the list to hold nothing else. An order with other lines as well is kept.

Containment ignores the fields the condition does not name.

Equality would need the whole document to match. @> asks only whether the document contains the one given.

Choosing

Read the section

Self-Check

1. A plant runs a historian on the floor, a relational database for orders and production, and a warehouse for analysis, each for the data it suits. What is this practice called?

Yes. A plant’s information systems usually practice it, and each of the databases still answers the two questions of where the description of the data lives and how records connect.

Eventual consistency concerns copies of one record that may briefly disagree, not the use of several kinds of database.

Schema on read concerns when a document’s structure is applied, not how many kinds of database a system uses.

Denormalization repeats facts within one design. Using several databases, each for its own data, is a different matter.

2. True or False: the designer of a NoSQL database usually starts from the business and lets the questions come later, as the designer of a relational database does.

A key-value store finds a record only by its key, and combining collections is often left to the program, so the records must be shaped for known questions.

Correct. A NoSQL design starts from the questions known in advance. A relational database answers any question its data can answer, which matters to an engineer whose next question is rarely the last one.
