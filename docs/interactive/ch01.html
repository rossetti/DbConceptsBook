From Files and Spreadsheets to Databases

Read the section

Self-Check

1. A hardware store opens an account with HG Industries in December, weeks before it places its first order. The sales office still keeps its orders in the order log, one row per order line. Which problem does the request to record the new store run into?

Nothing recorded about the store needs to change; the store is not in the log at all yet.

Yes. Every row of the log is a line of an order, so a customer with no order has no row to live in. The same problem keeps a new product out of the log until someone orders it.

Removing a fact is the opposite trouble: deleting an order’s only row also deletes what the log knew about its customer.

The rules concern values typed wrongly, such as a quantity of ten. Here the value is fine; there is simply no place for it.

2. Why does the order log store most of its facts many times?

The copies are not mistakes. They follow from what a row of the log is.

Yes. A customer’s city is written on every line of every order the customer places, and a product’s description on every line that orders it. Nothing ties the copies together.

A workbook can hold many sheets. The trouble is how the facts are arranged within a row, not how many sheets there are.

The order of the rows has nothing to do with how often a fact is repeated.

3. In HG Industries’ database, which of these bad entries does the chapter say the database refuses only if it is told to?

The chapter lists this among the entries the database refuses, since an order line refers to a product rather than copying it.

The chapter lists this among the entries the database refuses without being asked.

Yes. A date far in the future is still a date. The database refuses it only when a rule says what range of dates is sensible.

A database enforces the rules stored with the data. A rule nobody declared is not enforced.

2. An engineer queries HG Industries’ database in DataGrip, while a scheduling application written for the plant reads the same database. How does each reach the data?

People and programs do not open a database directly. The DBMS stores the rows and finds them.

Yes. Tools and programs alike send SQL to the DBMS, which does the work of storing and finding the data.

A program written for a purpose uses SQL to reach the database, just as a tool does.

Both use the same database through the DBMS. Nothing needs copying.

From a Model to a Database

Read the sections

Self-Check

1. Once the class model of a business is settled, which step of implementing turns it into tables with keys that link them?

Yes. Mapping turns the classes and their associations into tables, and the keys connect the tables as the associations connected the classes.

Normalization comes after mapping. It checks the tables so that each fact is stored once.

Queries use the tables once they exist and hold data.

The class diagram is the model itself, which this step starts from.

2. A reader writes a query meant to list each customer in the base data of HG Industries’ database once. It returns eleven rows. What should the reader conclude?

The point of a small database is that you need not take the computer’s word for it.

Yes. The base data is kept small on purpose so that you can check any query’s answer by hand. Here the check fails before the result reaches anyone else.

The base data holds eight customers. The customers that the year of history adds belong to a later stage, not to the base data.

A small database gives exact answers. Its size is what makes a wrong one easy to see.

3. An engineer is asked to build a database for a machine shop’s tool crib and begins by sketching tables and choosing data types. What does the chapter advise first?

Records show what happened to be written down, not what the business needs to record.

Yes. That is modeling, done independently of any software. Tables, keys, and types are implementation, answered by the model.

The model does not depend on any software, and the choice of DBMS comes after it.

Queries use a database that exists. What the database must hold comes first.

Self-Check

1. In HG Industries’ database, order SO-5002 is canceled and its order removed. What happens to what the database knows about Cedar Creek Home Center?

That is what happened in the spreadsheet log. The database records each customer once, in a table of customers, apart from its orders.

Yes. Removing the order removes the order, not the customer.

Nothing needs copying. The customer’s row was never part of the order.

A customer may exist with no orders, just as a product may exist before anyone orders it.

2. Which problems of the order log appear only once more than one person needs it? Select every one that does.

Select all that apply.

Yes. Sharing one file between people produces competing versions.

Yes. Each department’s file answers its own questions; a question that spans two files has no place to be asked.

This trouble arises even if one clerk keeps the log alone. It comes from storing the city many times.

This arises with a single user too. It comes from what a row of the log is.

3. The production department keeps a parts list in its own spreadsheet, and the quality department keeps another, both listing the same frame. Why does the chapter argue for one database instead?

Size is not the issue; a parts list fits in a spreadsheet easily.

Yes. The part that production makes is the part that quality inspects. The records of an industrial system form one connected body of data, and a database should connect them too.

Both departments record individual events as they happen, and both records can also be summarized.

A spreadsheet can store a description. The trouble is storing it twice with nothing to keep the copies the same.
