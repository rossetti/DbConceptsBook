Chapter 8 Self-Checks

Defining and Populating Tables

These questions follow the order of Chapter 8. Each of the first six groups checks one section of the chapter, and the last group reviews the whole chapter. The “Self-check” buttons in the chapter lead to these groups. Nothing you answer is recorded.

From a Design to Tables

Read the section

Self-Check

1. A colleague built a database by clicking through DataGrip’s dialogs and wants to know why the book writes every table as a statement in a script instead. Which reason is right?

The dialog is a convenience, not a different mechanism. It writes a CREATE statement and sends it to the server, as a script would.

Yes. A script that builds a database from nothing is its most useful description. A sequence of clicks cannot be read, kept, or run again.

The server receives the same statements either way. The difference is what you keep afterward.

Both tools can generate the DDL of an existing table, which is how a database built by hand is captured as a script.

2. PostgreSQL keeps a search path, and SET search_path TO distribution; lets a session write customer for distribution.customer. Why do the book’s scripts still write distribution.customer in full?

A name without a schema is allowed; PostgreSQL looks for it in the schemas of the search path.

Yes. A name written with its schema refers to the same table in every session, so the script does not depend on a setting it cannot see.

The search path is a list of schemas, not a single one.

The reason is that the name means the same thing everywhere, not speed.

Data Types

Read the section

Self-Check

1. A trucking firm records the moment each load is dispatched, from terminals in three time zones, and compares dispatch times across terminals. Which type suits the column?

A date drops the time of day, which the comparison needs.

A TIMESTAMP records a time without saying where, so 9:00 at two terminals in different zones would look like the same moment.

Yes. It records an instant, and displays it in the reader’s zone, so times from different terminals compare correctly.

Text sorts and compares as characters, not as moments, and two terminals may type the same time differently.

2. Which of these values suits a DOUBLE PRECISION column?

Yes. Floating point suits a quantity that is computed rather than recorded, such as a simulation’s output.

A count is a whole number, so it is an INTEGER.

A calendar date is a DATE, which compares and sorts as a date.

A name is text, a VARCHAR(n) or TEXT.

3. The order_number column is declared VARCHAR(10). What does the length limit do for the database, beyond saving space?

The limit is also a rule: a longer value is refused.

Yes. VARCHAR(n) holds text of up to n characters and refuses a longer value, so it catches one kind of error at the door.

That is what CHAR(n) does. VARCHAR(n) stores the value as given.

The limit is a maximum. Shorter values are accepted as they are.

Creating Tables and Constraints

Read the section

Self-Check

1. The CHECK (requested_ship_date >= order_date) of customer_order is written without a name, so PostgreSQL names it customer_order_check. When should you write CONSTRAINT some_name CHECK (...) instead?

PostgreSQL accepts an unnamed constraint and names it from its table and columns.

Yes. Every message that reports a violation names the constraint, so a name such as order_ship_after_order points straight at the rule.

Any constraint can be named, a check among them.

A named constraint is removed by its name, with ALTER TABLE ... DROP CONSTRAINT.

2. At stage D3, customer_order.customer_fk refers to customer. Someone runs DROP TABLE distribution.customer CASCADE. What happens to customer_order?

The cascade removes the foreign key constraints that depend on customer, not the tables that hold them.

Yes. The cascade drops the constraints that depend on customer and then the table, so customer_fk is left as a plain column that refers to nothing.

Dropping a constraint does not change any row’s values, and customer_fk is NOT NULL besides.

A plain DROP TABLE is refused for that reason. CASCADE is what lets it go ahead.

3. True or False: a script that copies customers from another database can insert each customer with its old customer_pk, since the column is the primary key, by listing customer_pk in an ordinary INSERT.

The column is declared GENERATED ALWAYS AS IDENTITY, so the database alone numbers its rows.

Correct. An ordinary INSERT that supplies a value for a GENERATED ALWAYS column is refused. The message’s hint names the override that a script copying rows, keys and all, would use.

Inserting, Updating, and Deleting Rows

Read the section

Self-Check

1. A script inserts customers with INSERT INTO distribution.customer VALUES (...), leaving out the column list. It works today. What happens after a column is added to customer?

Values are matched by position, not by type. Two text columns look the same to an insert.

Yes. Without a column list the values are matched to the columns in the order the table declared them, so a new column shifts the match. Always write the column list.

That happens only when the insert lists its columns and leaves the new one out.

The form is allowed. It is fragile, not illegal.

2. True or False: on a freshly loaded stage whose last customer key is 8, an insert of a new customer is refused by a constraint and the next insert is accepted. The accepted customer receives the key 9.

It would, if the database numbered rows by counting them or reused a value it had handed out.

Correct. A generated key comes from the column’s identity counter, and an insert takes the next value even when it is refused or rolled back. The value is never given back, so the accepted customer receives 10. Look a customer’s key up by its business number rather than assuming it.

3. A new customer is named Crowley’s Ridge Hardware. How is the name written as a value in an INSERT?

The quote inside the name would end the value after “Crowley”, and the rest would be read as a mistake.

Yes. A quote inside a text value is written twice, which is how SQL tells it from the quote that ends the value.

A text value is enclosed in single quotes; double quotes mean something else in SQL.

A text value must be enclosed in single quotes.

4. An INSERT INTO distribution.customer (...) SELECT ... FROM distribution.customer_staging WHERE state = 'TX' is run, and no staged row has the state TX. What happens?

A query that finds no rows is not an error, so nothing refuses the statement.

Yes. That is the one danger of the INSERT ... SELECT form that the VALUES form lacks. Count the rows the query returns before relying on the insert.

An INSERT ... SELECT adds exactly the rows the query returns, here none.

The WHERE clause chooses the rows, and it chose none.

Loading Data from Files

Read the section

Self-Check

1. Why is a CSV file loaded into a staging table of TEXT columns without constraints, rather than straight into its final table? Select every reason that applies.

Select all that apply.

Yes. The staging table accepts anything, so every row arrives and every problem can be found with queries.

Yes. No constraint catches it; only looking at the staged rows does.

\copy loads any table. The staging table is a choice made so that the rows can be examined first.

Yes. The move is a query, so it can trim, capitalize, and drop duplicates on the way.

2. A file of new customers is on your laptop, and you connect to a PostgreSQL server on another machine as an ordinary user. Which way of loading the file works?

COPY is run by the server and reads a file on the server’s own machine. It is also allowed only to superusers and roles granted pg_read_server_files.

Yes. \copy reads the file on your machine and sends its rows to the server, needs no special privilege, and takes the same options as COPY. The import wizards of DataGrip and DBeaver would also work.

Only COPY needs the file on the server. \copy and the tools’ import wizards read it where it is.

A file name is not a table, so a query cannot select from it.

3. Two staged rows share the customer number C-1015, but one spells the city differently. The rows are moved with INSERT INTO distribution.customer (...) SELECT DISTINCT ... FROM distribution.customer_staging. What happens?

DISTINCT removes only rows that are identical in every column, and these two differ in the city.

Yes. A duplicate with two versions needs a person to decide which is right, which is why a staging query should count the different versions of each repeated number before the move.

customer_number is UNIQUE, so the database will not hold two.

A statement that breaks a constraint is refused as a whole; no row of it is kept.

Changing a Table’s Definition

Read the section

Self-Check

1. The stage P1 script fills a new column of product with an UPDATE that joins it to production.part. The book also shows the standard form, which sets the column to a correlated subquery. Which form is PostgreSQL’s own?

Yes. UPDATE ... FROM joins the table being updated to another. It is PostgreSQL’s form, and both give the same result here.

Setting a column to a correlated subquery is the standard form.

That adds the column. It does not fill it.

The standard has the subquery form only.

2. ALTER TABLE distribution.customer ADD CONSTRAINT customer_state_in_capitals CHECK (state = UPPER(state)) has been run, and every existing customer satisfies it. A later insert gives a customer the state ok. What happens?

A constraint added to a table applies to every later change, however the table was first created.

Yes. The name was chosen so that the message names the rule that was broken.

A check refuses a value; it never changes one.

The database keeps the rule and refuses the row.

3. True or False: once ALTER TABLE has added a column to the running database, the change is kept even if the database is later rebuilt from its scripts.

A rebuild runs the scripts, and a change that is not in them is lost.

Correct. Every change to a running database belongs in the scripts that rebuild it. The book’s database adds each change as a stage script that runs after the ones before it: the scripts, not the running database, are the definition.

Review of the Whole Chapter

Read the chapter summary

Self-Check

1. The sales department states two rules: every customer must have a city, and no two customers may share a customer number. The customer table already has customer_pk as its primary key. Which declarations implement both rules?

Yes. NOT NULL makes a column required, and UNIQUE declares an alternate key, so the database refuses a second customer with an existing number.

UNIQUE on city would stop two customers from sharing a city, which the business allows, and it does not require a city.

A table has one primary key. A second identifier is an alternate key, declared UNIQUE.

NOT NULL requires a number but lets two customers share one.

2. A spreadsheet’s order dates were loaded into a text column, written as 9/2/2026 and 10/2/2026. A query sorts the orders by that column. What goes wrong?

Text sorts character by character, not by calendar.

Yes. The type accepts the value and then misbehaves. A DATE column sorts and compares as dates.

Text can be sorted; it is sorted as text.

PostgreSQL sorts a text column as text unless the query converts it.

3. The order_line table has primary, alternate, and foreign keys and checks on its quantity, price, and line number. Which business rule do these constraints leave unenforced?

The foreign key on product_fk enforces that.

The alternate key on customer_order_fk and line_number enforces that.

Yes. The constraints check each line alone, so an order with no lines is accepted, though the class model says an order has one or more. A query must find such orders.

ON DELETE CASCADE on customer_order_fk deletes the lines with the order.
