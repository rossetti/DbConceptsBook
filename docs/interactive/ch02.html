Tables, Rows, and Domains

Read the section

Self-Check

1. A designer stores each part’s dimensions in one text column, as values such as 24 x 18 x 10 (length, width, and depth in inches). Planners regularly ask which parts fit on a shelf 20 inches deep. Is the dimensions value atomic?

Holding one string is not the test. “Fayetteville, AR” is one string too.

Yes. The test is a question about use: does any query, rule, or sort need part of the value on its own, in a way its domain does not supply? Here one does, so the three measures belong in separate columns.

Length does not settle it. A two-character state code is atomic and a long description may be too, depending on how each is used.

“Fort Smith” contains a space and is atomic. How a value looks does not settle the question.

2. Which of these changes alters the customer table’s schema rather than its state?

Yes. The schema is the table’s name, columns, and domains, and it changes when the database is redesigned.

A new row changes the rows the table holds now, which is its state.

Changing a value in a row changes the state.

Removing a row changes the state. The table can still hold exactly what it could hold before.

The schema is what the database can hold, and the state is what it holds now.

3. A designer gives an order table the columns product1, product2, and product3, one product number in each. What is wrong with this design?

Each cell does hold one value, but the three columns hold the same attribute, told apart only by position.

Yes. The relational model forbids repeating groups and records such facts as rows of a table of their own, one row per product on the order.

The three names are different, so the third property holds. The trouble is what the columns hold, not what they are called.

The order of the columns carries no meaning. Reordering them changes nothing about the design.

4. A script adds rows to a table with INSERT statements that list values but do not name the columns. Later the table is rebuilt with the same columns declared in another order. What happens when the script runs again?

That is the model. A SQL table keeps the order in which its columns were declared, and such a statement depends on it.

Yes. A statement that adds a row without naming its columns matches values to columns by position. A statement that adds a row should always name its columns.

The database does not guess. It matches values to columns by position when no columns are named.

The statement adds the same rows as before. The trouble is which column receives which value.

Keys

Read the section

Self-Check

1. customer_number is a candidate key because HG Industries assigns each customer one number and never reuses it. Suppose the company began giving a closed customer’s number to a new customer. What follows?

Yes. A candidate key is a fact about the business, so it holds only as long as the business’s rule does.

customer_pk is generated by the database. How the business numbers its customers does not affect it.

The key rests on the business’s promise. When the promise changes, the key goes with it, whatever the tables say.

A surrogate key is a value the database generates, meaning nothing outside it. A customer number is business data either way.

2. Is the pair (customer_number, city) a candidate key of the customer table?

That makes the pair a superkey. A candidate key must also be minimal.

Yes. A column can be removed from the pair without losing the property, so the pair breaks the second condition.

A key of several columns, a composite key, is a candidate key when no smaller set of its columns would do.

An extra column makes the set larger, not safer. It is still a superkey, but not a candidate key.

3. The stock_level table has the alternate key (warehouse_fk, product_fk). A clerk receives 50 more units of a product that a warehouse already stocks and tries to record them by adding a new stock_level row for that warehouse and product. What happens, and what should the clerk do?

The alternate key forbids two rows with the same warehouse and product, so the database never holds the second row.

Yes. The key says that a warehouse holds at most one stock level for each product. Neither column alone is a key: a warehouse stocks many products, and a product is stocked in more than one warehouse.

Both columns are foreign keys, and together they are a key. A column may play both roles.

A new surrogate key does not excuse a row from the alternate key. The database enforces every candidate key.

4. At stage D2, customer 1 appears three times in the customer_fk column of customer_order, and customer 8 does not appear at all. What does that pattern show? Select every statement it supports.

Select all that apply.

Yes. Each of customer 1’s orders holds the same customer_fk.

Yes. Nothing requires a customer to be referred to by any order.

A foreign key’s values may repeat. It is the key it refers to, customer_pk, whose values may not.

The rule concerns the values of a foreign key. A customer that no order refers to breaks nothing.

Integrity Rules

Read the section

Self-Check

1. A designer declares a foreign key’s response to deleting the row it refers to as SET DEFAULT. What must be true for a deletion to succeed under that response?

A response that leaves the rows referring to nothing is SET NULL, a different response.

Yes. The rows that referred to the deleted row are given the default, and referential integrity still applies to it: a default that matches no row would leave them pointing at nothing.

The new value is a foreign key value like any other, and the rule applies to it.

A row that nothing refers to is deleted without any response at all. The response matters only for rows that are referred to.

2. A query lists each order beside the name of the customer who placed it, by matching customer_fk to customer_pk. Can an order’s customer_fk hold a value that matches no customer?

Yes. A foreign key is a promise the database keeps on every change, so the query never has to check for orphans itself.

Whatever response the designer declared, the database never leaves an order pointing at a customer that does not exist.

The database checks a foreign key when a row is added or changed, before the change is kept.

How a query is written cannot change the rows a table holds.

Writing Down a Schema

Read the section

Self-Check

1. The complete relational schema of customer_order includes the line check: requested_ship_date >= order_date. What does it say?

Yes. A CHECK constraint narrows the domain of a column, here by comparing it with another column of the same row.

Whether a column may be NULL is said on its own column line, and requested_ship_date may be NULL.

The check compares two columns of the order itself. Shipments and their dates are recorded in another table.

A CHECK constraint is part of the schema, and the database enforces it on every change.

2. The foreign key lines of the distribution schema sort its tables into groups. Which of its tables refer to no other table of the distribution schema? Select every one that does not.

Select all that apply.

Yes. It has no foreign key.

Yes. It has no foreign key.

Yes. Its one foreign key refers to production.manufactured_part, a table of another schema.

An order refers to the customer who placed it.

A stock level refers to a warehouse and to a product.

3. A bill of materials line has the columns assembly_fk and component_fk. What do the book’s naming rules tell you about them?

A primary key column ends in _pk. A table has one primary key, and these columns end in _fk.

Yes. A line names an assembly and one of its components, both parts, so naming each column after its table would not say which is which.

A foreign key is usually named for the table it refers to, but these are named for roles, since the rows they refer to are all parts.

The relational schema states the keys anyway: a key of several columns, an alternate key, and a database named by someone else’s rules all need saying.

The Catalog and the Tools That Read It

Read the sections

Self-Check

1. A query names the column order_no, but the column of customer_order is named order_number. When does PostgreSQL find the mistake?

The DBMS never gets that far. It checks every table and column a query names first.

Yes. The DBMS reads the catalog more than anyone, and it refuses a query that names a column the table does not have.

A query that names a missing column produces no result at all, empty or otherwise.

The database does not guess at names. It refuses the query and says which column does not exist.

2. Which of these changes alter the catalog? Select every one that does.

Select all that apply.

Yes. Creating a table adds rows to the catalog, which describes the table and its columns.

Yes. A new column is a change to the schema, and the catalog holds the schema.

A new row changes the state of the customer table, not its description.

Changing a value changes the state. The catalog changes only when the database is redesigned.

3. Why does the database tree of DataGrip or DBeaver have the same outline for any PostgreSQL database you connect to, even one you have never seen?

Those are HG Industries’ schemas. Another database has schemas of its own, and the tree shows them just the same.

Yes. A relational database is self-describing, so you can always ask it what it holds. psql’s \d command reads the same catalog.

The tool reads the schema from the database each time it connects. It brings no copy with it.

The tree shows each database’s own schemas, tables, columns, keys, and constraints.

Other Ways to Organize Data

Read the section

Self-Check

1. Which statement separates the relational model from the hierarchical and network databases that came before it?

Where the data is kept is not the difference the chapter draws.

Yes. Because tables connect by values, any question can be asked in a query; in the older databases, an unplanned question meant a new program to walk the links.

A bill of materials is a tree, which suited a hierarchical database well.

The relational model replaced them for most uses, but IMS still runs in some banks and manufacturers.

2. A document database stores order SO-5001 as one JSON document, with the order’s lines nested inside it. What does a program gain from that arrangement?

Yes. A document database suits data that is written and read whole, such as an order or a test record.

Each document describes itself, and no catalog is needed to read it.

The lines are nested inside the order’s document, as a list.

A field may hold a number, a list, or another document.

Review of the Whole Chapter

1. Why does a SQL table need a key to keep the property that no two of its rows are identical?

A key identifies rows. It has nothing to do with sorting them.

Yes. Every table in the book’s database has a key, and the database rejects any row that would repeat a key value.

PostgreSQL will create a table with no key. That is why the key must be declared.

A query result may repeat a row, but so may a table with no key. The key is what prevents it in the table.

2. What was the appeal of an object database, which stores a program’s objects directly?

An object database connects objects by references, as the objects of a running program are connected.

Yes. Object databases never displaced relational ones; relational systems took on some of their features, and libraries now do the translation.

That describes a document database, whose documents describe themselves.

It found uses there, but it never displaced relational databases.
