The Shape of an Analytical Query and Grouping

Read the sections

Self-Check

1. A query computes COUNT(*), SUM(quantity), MIN(unit_price), MAX(unit_price), and AVG(unit_price) over the 22 order lines of stage D5, with no GROUP BY. How many rows does it return?

An aggregate returns one value from many rows. The lines are summarized, not listed.

The aggregates are columns of the result, not rows.

Yes. Without GROUP BY, every aggregate is computed over all the rows that the WHERE clause kept, and the result has exactly one row.

An aggregate may summarize the whole table. GROUP BY is needed only to have one summary per group.

2. A query groups the order lines by product_fk, unit_price. What does each group hold?

That would be GROUP BY product_fk. Adding unit_price divides each product’s lines further.

Yes. A group is formed for each different combination of the grouping columns. That answers a different question from the units of each product.

The groups are formed by both columns together, so two products at the same price stay apart.

Several lines of a product often share a price, and they share a group.

3. Which aggregate gives each product’s total value ordered, the sum of quantity times unit price over its lines, when the lines are grouped by product?

Yes. An aggregate may take any expression: the product is computed for each line, and then the values are summed.

This multiplies the total units by the sum of every line’s price, which is no value at all.

This matches the total only when every line of the product has the same price. A large line at a low price makes it wrong.

COUNT(*) counts lines, not units, and the highest price is not the price of every line.

4. A query counts orders by month with GROUP BY EXTRACT(MONTH FROM order_date), over the orders placed from January 2026 through March 2027. What goes wrong?

EXTRACT(MONTH ...) gives only the month’s number, 1 to 12, whatever the year.

Yes. A group is formed for each different value of the grouping expression, and the month’s number alone does not tell the two years apart. Grouping by the year as well keeps them apart.

A group may be formed by any expression, not only a column.

Orders placed in the same month share a value of the expression, and so share a group.

Filtering Groups

Read the section

Self-Check

1. The counting method finds the operators certified on every Machining machine: it counts each operator’s certifications on Machining machines and keeps the operators whose count equals the number of Machining machines. What makes counting certifications the same as counting machines?

Yes. Without that key, a repeated certification would be counted twice, and an operator certified twice on one machine would look certified on two.

COUNT(*) counts rows. It is the key that rules out a second row for the same operator and machine.

HAVING keeps or discards whole groups. It removes nothing within one.

An operator may hold many certifications. The key limits each operator to one for each machine.

2. In the same counting query, the condition m.work_center_fk = 2 in WHERE keeps only the certifications on Machining machines. Suppose it were left out, while HAVING still compares each count with the number of Machining machines, which is 2. What would go wrong?

The subquery in HAVING counts Machining’s machines. It does not restrict which certifications each operator’s group counts.

Yes. The rows must be restricted to the work center before they are grouped and counted, which is the job of WHERE.

Only the operators with exactly two certifications in all would be kept, which is still the wrong list.

The query is valid. It answers a different question, with no message.

3. A planner wants the largest number of orders placed in any one month. Which approach gives it, and still shows every month if two months tie?

A window function cannot be tested in WHERE, which is evaluated before it.

This finds the busiest month, but a tie would show only one of the tied months.

Yes. The first step groups and the second summarizes the groups. Keeping every month equal to the maximum keeps all the tied months.

This keeps every month that had an order; it does not pick out the busiest.

CASE Expressions

Read the section

Self-Check

1. Which value does this expression give an order line of 25 units?

CASE
  WHEN quantity >= 10 THEN 'large'
  WHEN quantity >= 20 THEN 'very large'
  ELSE 'small'
END

Yes. The conditions are tested in order, and the value of the first true one is returned. Since every line of 20 units or more also has 10 or more, 'very large' can never be returned; the larger threshold must be tested first.

The second condition is true, but the first already was, and CASE stops at the first true condition.

A CASE expression returns one value for each row.

ELSE is reached only when no condition is true.

2. When may a CASE expression be written in the shorter form CASE unit_of_measure WHEN 'EA' THEN 'each' WHEN 'FT' THEN 'feet' ELSE 'unknown' END?

Yes. The shorter form names the expression once, after CASE, and each WHEN gives a value to match.

The shorter form may have an ELSE, as this one does.

A range is not a match with one value. Such conditions need the full form, with a condition in each WHEN.

A CASE expression of either form may stand anywhere a value may.

3. The production manager’s morning list sorts the work orders with ORDER BY CASE WHEN completed_on IS NULL THEN 1 WHEN completed_on > due_on THEN 2 ELSE 3 END, due_on, work_order_number. Which statement about it is true?

A CASE expression may stand anywhere a value may. Here it is used only to sort.

Yes. The open work orders lead, then the late ones, then the rest. A sort like this replaces a report’s hand-arranged sections.

The expressions sort in the order they are named, so the rank comes first.

Nothing is grouped. The expression is computed for each row and used as a sort key.

Window Functions

Read the section

Self-Check

1. Suppose four customers placed 45, 45, 40, and 38 orders. A query ranks them with RANK() OVER (ORDER BY COUNT(*) DESC) and with DENSE_RANK() over the same order. What ranks does each give the customer with 40 orders?

DENSE_RANK skips nothing after a tie.

RANK skips the ranks that tied rows use up.

Yes. Both give the two tied customers rank 1. RANK then gives 3, since two customers finished ahead, and DENSE_RANK gives the next rank, 2.

This reverses the two functions.

2. Suppose a product has four order lines: 10 units ordered on January 5, 5 units and 15 units both ordered on January 9, and 20 units ordered on January 12. What does SUM(quantity) OVER (ORDER BY order_date) show on the line of 5 units?

That counts the rows one at a time. The default frame also takes in the current row’s peers, the rows that tie with it on the ORDER BY columns.

Yes. With an ORDER BY and no explicit frame, the frame runs from the first row to the current row and its peers. Both January 9 lines are in it, so both show 10 + 5 + 15 = 30.

The frame ends at the current row’s last peer, not at the end of the partition.

The frame begins at the partition’s first row, so the running total includes January 5.

3. A five-inspection moving average uses ROWS BETWEEN 4 PRECEDING AND CURRENT ROW, ordered by inspection time. The axle diameter was inspected once on each weekday from June 8 to 16, 2026, and not on June 13 and 14, a weekend. Which inspections are in the frame of June 16?

ROWS counts rows, not days. The weekend holds no rows, so the frame reaches further back.

Yes. The frame holds the current row and the four rows before it, whatever their dates.

The frame holds five rows at most: the current row and the four before it.

4 PRECEDING adds four rows to the current row, so the frame holds five.

4. Which of these requests need two steps, a common table expression that computes the window function and a query that reads it? Select every one that does.

Select all that apply.

Yes. A window function cannot appear in WHERE or HAVING, since both are evaluated before it, so the filter on its result is a second step.

Yes. The product’s average comes from a window function, and the condition that compares each line with it cannot be written in WHERE, so it is a second step.

One query does this, with AVG(unit_price) OVER (PARTITION BY product_fk).

LAG in a single query does this, since nothing is filtered on its result.

Recursive Queries

Read the section

Self-Check

1. Suppose a data-entry error records part A as a component of part B, and part B as a component of part A. What happens when a bill of materials explosion reaches them?

Nothing in a plain recursive query compares a new row with earlier ones; with UNION ALL a part found again is simply added again.

Each step finds the other part again, so the two never stop producing rows.

Yes. A recursive query stops only when a step produces no rows. A condition such as WHERE e.depth < 20 in the recursive part, or the CYCLE clause of PostgreSQL 14 and later, ends it.

The anchor finds the starting product as usual; the trouble begins in the steps below it.

2. True or False: in each run of the recursive part, the database joins every row found so far to bom_line.

If it did, a part found in an earlier step would be exploded again in every later step, and its components would be repeated.

Correct. Each run sees only the working table, the rows the previous step produced. A part found in step 1 is exploded in step 2 and not again.

3. A bill of materials uses the same hardware kit in two places in one product’s structure. Which choice between UNION and UNION ALL in the recursive query is right for a quantity explosion, and why?

UNION removes rows that repeat exactly, so when both places give the same row the second is lost, and the kit’s quantity is understated.

Yes. Each place contributes its own quantity, and keeping every row keeps them all. UNION suits a list of distinct parts, not quantities.

They happen to agree only when no row repeats exactly; an explosion should not depend on that.

A recursive common table expression is an anchor and a recursive part joined by a union.

4. Suppose one product uses 3 of an assembly, each assembly uses 4 of a component, and each component is cut from 0.5 feet of bar stock. How many feet of bar stock does the explosion report for one product?

That is the bar stock in one component. The quantities multiply down the chain.

This adds the quantities. Each level multiplies its parent’s quantity by the component’s quantity_per.

Yes. 3 assemblies times 4 components each is 12 components, and 12 times 0.5 feet is 6 feet.

That is the number of components; each needs only half a foot of bar stock.

Analytical Queries on Operational Data

Read the section

Self-Check

1. The days-of-supply query divides each stock level’s quantity on hand, from the stock_level table, by a daily rate computed from a year of shipments. The year of history in stage G does not update stock_level. What does the result therefore measure?

The stock levels hold one recorded quantity each. Nothing in them changes from day to day.

Yes. The comparison is still useful for ranking urgency, but its stock figures are the ones on record, not the result of the year’s shipments.

The query subtracts nothing. It divides the recorded quantity by the daily rate.

The query reads one quantity per stock level, not a history of quantities.

2. An individuals chart’s limits are computed from the average moving range, the absolute difference between consecutive measurements, found with LAG. Which statements about that query are true? Select every one that is.

Select all that apply.

Yes. LAG is a window function, computed after any grouping, so the averages of its results come in a second step.

Yes. The limits are the center line, the average measurement, plus and minus 2.66 times the average moving range.

LAG is a window function, which cannot appear in HAVING, and nothing here is grouped.

Control limits come from the process’s own variation, not from the specification. A point outside them signals a cause worth investigating.

3. A days-of-supply query divides a year’s units shipped by 365 to get each product’s daily rate. For a product first sold in September of that year, what does that do to its days of supply?

The total is right, but it is spread over months in which the product was not for sale.

Yes. The units were sold over about seven months, not twelve, so the true daily rate is higher.

Dividing by more days than the product was sold makes the rate smaller, not larger.

The product has shipments, so its sum and rate are numbers, just misleading ones.

Self-Check

1. Which of these requests need a window function, rather than GROUP BY alone? Select every one that does.

Select all that apply.

Yes. GROUP BY keeps one row per product; a window function keeps every line and adds its group’s average.

Yes. SUM with an ORDER BY inside OVER gives each row the total of its frame.

Yes. LAG reaches into the previous row of the order.

One row per product is exactly what GROUP BY returns.

One row per month is exactly what GROUP BY returns.

2. A query has a WHERE clause, a GROUP BY, a HAVING clause, and a window function in its SELECT list. Which statement about it is true?

HAVING is evaluated before the window function, and PostgreSQL refuses a window function there.

Yes. This is how a query ranks customers by their number of orders in one step.

Window functions are computed after GROUP BY, HAVING, and the SELECT list, over one row for each group.

DISTINCT comes after the window functions in the order of evaluation.

3. A quality engineer asks for the median completion time of the completed work orders for each manufactured part. Which parts does the query need? Select every one it does.

Select all that apply.

Yes. “For each manufactured part” names the groups.

Yes. The median is the 0.5 percentile, and the values it orders are named after WITHIN GROUP.

The request wants one row per manufactured part, not every work order beside its group’s median.

Nothing in the request follows a chain of rows.

The order a percentile needs is given inside the aggregate, after WITHIN GROUP. Sorting the result computes nothing.
