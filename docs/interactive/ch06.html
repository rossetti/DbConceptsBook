Chapter 6 Self-Checks

From Class Models to Tables

These questions follow the order of Chapter 6. Each of the first five groups checks one or two sections of the chapter, and the last group reviews the whole chapter. The “Self-check” buttons in the chapter lead to these groups. Nothing you answer is recorded.

The Mapping Process and Mapping Classes

Read the sections

Self-Check

1. A designer maps the classes of a model one at a time: the first class with its attributes, keys, and associations, then the second, and so on. Why does the mapping instead apply each step to the whole model before taking the next step?

The order of the steps has nothing to do with how the database creates tables. It comes from what each step needs.

Yes. An association cannot become a foreign key until the table it refers to exists and has its primary key, so all the classes and their keys come first.

The class model may be revised whenever a check shows it is wrong, not only between steps.

All the steps produce one relational schema, built up step by step.

2. The class ManufacturedPart has an attribute lotSize. What are the table and the column called?

Tables and columns are named in snake_case, not in the capitalized style of class and attribute names.

Yes. Each name is written in snake_case, and the table keeps the singular of the class, since it implements a class that describes one object.

The table is named in the singular, like the class it implements.

A class maps to a table named for that class, not for another.

3. A hypothetical Supplier class has a business identifier supplierNumber, a name, and a minimumOrderValue that must be positive. Which of these does mapping the class give the supplier table? Select every one that does.

Select all that apply.

Yes. The business promises that no two suppliers share a number, so the column is an alternate key.

Yes. No SQL type holds only positive amounts, so a CHECK implements the narrower domain.

Yes. A class model names no identifier; the mapping supplies one, under the book’s convention a surrogate key supplier_pk.

Free text is a type, not a multiplicity. With no [0..1] on the attribute, the column is NOT NULL.

Two suppliers may well have the same minimum. Only a value the business promises is never shared becomes a key.

4. In the last step of the mapping, a designer puts a few objects and links from a cloud instance diagram into the new tables as rows, and the rows cannot hold what the diagram shows. What should the designer do?

Patching the tables hides the problem. A table that cannot hold the diagram’s links says that the model or the mapping is wrong.

The diagram shows what the business records. Dropping the objects that do not fit throws away a requirement.

Yes. A check that fails sends the designer back to the class model, and the diagram shows where the trouble is. When a mapping seems hard, the trouble is usually in the model, not the rules.

A failed check is a finding, not a formality. The tables would lose or contradict data.

Mapping Associations

Read the section

Self-Check

1. Each work order is for exactly one part, and a part may have any number of work orders: Part 1 -- 0..* WorkOrder. How does the association map?

A part may have many work orders, so its row cannot hold its links as a single value. This puts the foreign key on the wrong side.

Yes. A one-to-many association maps to a foreign key in the table of the many end, and the minimum of 1 at the Part end makes it NOT NULL.

The side is right, but the 1 at the Part end has a minimum of one: every work order has its part.

A table of its own is needed only when neither end can hold its links as one value. Here each work order has exactly one part.

2. Customer 1 -- 0..* CustomerOrder maps to the foreign key customer_fk in customer_order, NOT NULL. What does the 0..* at the CustomerOrder end add to the tables?

A count can be computed from the orders whenever it is wanted; storing it would record a fact twice.

No check is needed to allow something the tables already allow.

Yes. A minimum of zero and a maximum of many are what a foreign key at the many end allows by itself.

A customer may have many orders, so its row cannot hold its links as one value.

3. A hypothetical operator table records each operator’s lead in lead_fk, a foreign key to operator_pk in the same table. How does a query find the crew of a given lead?

A lead may have any number of crew members, so the lead’s row cannot hold them as one value. It holds only its own lead.

Yes. A lead’s crew is found from the other side, just as a customer’s orders are the rows whose customer_fk is the customer’s key.

The lead’s own lead_fk leads up, to the lead’s lead, not down to the crew.

The one foreign key records every link. The crew is read from the rows that point to the lead.

4. Both ends of a one-to-one association are 1, and the two objects are always created and removed together. Besides a UNIQUE foreign key on one side, which mapping does the chapter offer?

Two foreign keys record each link twice and can disagree.

Yes. When the two objects come and go together, nothing is lost by storing them in one row.

A table of its own is the choice for two 0..1 ends, where a foreign key on either side would often be NULL.

A one-to-one association maps readily, by a UNIQUE foreign key or, here, by one table.

Mapping Qualified Associations

Read the section

Self-Check

1. In the mapping of the order line, the alternate key (customer_order_fk, line_number) keeps the qualifier’s meaning in the tables. Which rule of class models does the chapter call it the order line’s version of?

That rule decides which columns are NOT NULL, not which are keys.

Yes. Here the pair is an order and a line number, and the key allows at most one line for each pair.

That rule decides what a deletion does to the foreign key, not which columns form a key.

Inheritance concerns generalization, which an order line does not take part in.

2. The construct-by-construct ledger of the refined order model maps classes, business identifiers, attributes, and associations. One column of the resulting order_line table has no row of that ledger to come from. Which one, and why?

The unit price is an attribute of OrderLine, recorded for each line, and the ledger maps it with the other attributes.

Yes. The ledger leaves it for the mapping of qualified associations, where it becomes part of a key.

The association between OrderLine and Product has its row in the ledger, and product_fk is its result.

The ledger’s first row gives every table its surrogate key, order_line_pk among them.

3. A qualified association is mapped in which step of the mapping process?

A qualifier belongs to an association; it does not name a class of its own.

Step 3 gives each table its primary key and its business identifiers as alternate keys. The qualifier’s key comes with its association.

Yes. A qualified association is an association, so it is mapped with the others, after the classes and their keys exist.

Step 7 checks the tables the earlier steps built. It maps nothing new.

Mapping Generalization

Read the section

Self-Check

1. The parts are mapped with a table for each class: part holds part_number and description, and manufactured_part holds lot_size. A report needs the part number and lot size of every manufactured part. What does its query need?

In this mapping the inherited attributes stay in the superclass table. A manufactured part is split across two tables.

part_number is not a column of manufactured_part. The subclass table holds only its own attributes and the shared key.

Yes. The subclass table’s primary key, part_fk, is also its foreign key to part, so a manufactured part has the same key value in both tables, and the join puts the whole object back together.

That lists every part, not the manufactured parts the report asks for.

2. True or False: with a table for each class, the database refuses a part that has a row in both manufactured_part and purchased_part.

Each subclass table’s foreign key checks only that the part exists. Nothing compares the two subclass tables.

Correct. This mapping does not keep {disjoint, complete}: a part may be in both subclass tables, or in neither. A checking query finds such parts after the fact; it does not prevent them.

3. In the mapping of a generalization to one table, the column part_kind holds manufactured or purchased for each row. What is such a column called?

Yes. A discriminator says which subclass each row belongs to, so that one table can hold the objects of every subclass.

A qualifier belongs to an association end. part_kind belongs to each row of the table itself.

A surrogate key identifies a row. Many rows share each value of part_kind.

part_kind holds a word, not a reference to another table’s key.

4. True or False: the one-table mapping of a generalization violates a normal form, since many of its rows leave some columns NULL.

Older material sometimes says so, but NULLs alone do not break a normal form.

Right. Every column still depends on the key. The cost of the mapping is the NULLs themselves and what its foreign keys can no longer tell apart.

Choosing and Naming Keys

Read the section

Self-Check

1. The customer table has the surrogate primary key customer_pk, and the designer leaves customer_number without a UNIQUE constraint, since the table already has a key. A clerk then enters customer C-1001 a second time. What happens?

The primary key compares surrogate values, and the second row receives a new one.

Yes. A surrogate key adds to the natural key; it does not replace it. Only the UNIQUE constraint on the business identifier stops the duplicate.

A database never merges rows on its own. It accepts a row or refuses it.

NOT NULL requires a value; it does not compare one row’s value with another’s.

2. Blaha and Premerlani, whose method of mapping the book follows, call the two kinds of primary key value-based and existence-based identity. Which is a surrogate key?

Value-based identity is a natural key, made of the class’s own attributes, such as a part’s number.

Yes. A surrogate key identifies a row because the row exists, not by any value the business records. PostgreSQL generates it, and it means nothing outside the database.

The book’s database gives every table a surrogate primary key.

The kind of identity depends on where the key comes from, not on its type.

3. True or False: PostgreSQL checks a foreign key of two columns even when one of the two columns in the referring row is NULL.

PostgreSQL does not check a composite foreign key when any of its columns is NULL.

Right. A row with a NULL in one column of a composite foreign key passes the foreign key unchecked, so a design that relies on such a key declares its columns NOT NULL.

Review of the Whole Chapter

Read the chapter summary

Self-Check

1. Designing a database has two phases. This chapter’s mapping is the first, from a class model to a relational schema. What is the second?

The class model comes before the mapping; it is what the first phase starts from.

Yes. The complete relational schema holds everything those statements need: columns, types, NULL rules, keys, checks, and deletion rules.

Normal form is reviewed in step 7 of the mapping itself, on the tables.

Data is loaded once the tables exist. Creating them is the second phase of the design.

2. Which of these rules do the tables leave to a checking query, so that the database accepts data that breaks them? Select every one.

Select all that apply.

Yes. Nothing stops a part from being in both subclass tables, or in neither.

Yes. A CHECK refuses an operator as the operator’s own lead, but a longer loop satisfies both the foreign key and the CHECK.

The CHECK on quantity refuses a quantity of zero or less.

The foreign key product_fk refuses a line for a product that is not in product.

A CHECK that assembly_fk differs from component_fk refuses that.

3. Which of these constructs of a class model map to a table of their own, rather than to a foreign key in an existing table? Select every one.

Select all that apply.

Yes. Neither end’s table can hold its links as one value, so the links become rows of a table of their own.

Yes. Each link connects three objects, so each row holds three foreign keys, which together are a key.

Each order has one customer, so the link fits in the order’s row as a foreign key.

Each line belongs to exactly one order, so the link fits in the line’s own row, as a foreign key.

Each operator has at most one lead, so the link fits in the operator’s own row, as a foreign key to its own table.
