Operational and Analytical Processing

Read the section

Self-Check

1. Which description fits online analytical processing (OLAP) rather than online transaction processing (OLTP)?

That is OLTP, the work of the clerks and programs that run the business.

Yes. Analysis reads a great deal of history to answer one question, which makes the opposite demands on a design from taking orders.

Analysis works on history, added in periodic loads; seeing every change at once is the concern of the operational database.

Analysis reads. The rows of a warehouse are added by periodic loads, not changed by the people who analyze them.

2. A proposal would have each clerk’s correction to an order line change the matching fact in the warehouse the moment it is made. Which property of a data warehouse would that design give up?

The warehouse would still be organized around sales. What changes is how its rows are written.

Orders and standard costs would still be combined in one place.

Every fact would still be tied to a date.

Yes. A warehouse’s rows are added by periodic loads and are not updated by the business’s daily work. That is what gives the analyst a stable copy while orders are changing.

3. Against the operational tables, a sales report finds each product’s line with a CASE on the pattern of its product number. In the warehouse, the product line is a column of the product dimension. What is the main gain?

The warehouse’s query still joins the fact table to its dimensions. What it no longer needs is a derivation.

Yes. Each analyst groups by a column named for what it means, instead of re-deriving it, perhaps differently, in each query.

The two agree to the cent, since the warehouse was loaded from the same order lines. The difference is in the asking.

It can, and the operational query does exactly that. The trouble is that every query must repeat it.

Dimensional Modeling

Read the section

Self-Check

1. The sales warehouse’s fact table has the grain of one order line. The sales manager now wants to analyze the freight charged on each order, a single amount for the whole order. Where does the freight charge belong?

Stored on every line, the freight would be added once per line, so any sum of it over an order with three lines triples it.

This mixes two grains in one table. A line’s freight would then mean nothing, and the fact would look like a per-line amount when it is not.

Yes. The grain limits the facts: a fact that belongs to a whole order belongs in a fact table whose rows are orders.

A dimension holds the attributes an analyst groups by, not numbers measured each time the process runs. Freight is a fact.

2. The sales manager asks how often orders ship by their requested ship date. Where does the sales warehouse’s design say the answer belongs?

The design records each order at its order date only. It holds nothing about shipments.

Yes. A warehouse describes one business process at a time, and shipping is a different process from order taking.

A dimension holds the attributes an analyst groups by. Whether an order shipped on time is something that happened, not a description of the customer.

The date dimension describes days. It records nothing that happened on them.

3. In order_line_fact, the order number and line number are stored on the fact itself, with no dimension table behind them. Which statements about them are true? Select every one that is.

Select all that apply.

The fact table’s only foreign keys are those to its three dimensions. The order and line numbers are plain identifiers, kept so that an analyst can find the order.

Yes. They connect the warehouse to the operational order.

Yes. They are the fact table’s alternate key, and the incremental load tests them to skip what is already there.

An order dimension would hold nothing but the numbers themselves. With nothing to describe, the identifier stays on the fact.

4. A later design adds each order line’s requested ship date to the sales warehouse, so that facts can also be grouped by the month they were due to ship. How does the design add it?

Yes. One date dimension serves every date a fact has, and the name of each foreign key, such as order_date_fk, says which date it is.

A second copy of the same days adds nothing. One date dimension serves every date a fact has, each through a foreign key of its own.

Then a report could group by the ship date’s month only by deriving it in each query, which is what the date dimension spares it.

A foreign key holds one value, and this one already names the order date.

Extract, Transform, and Load

Self-Check

1. Which of these belong to the transform step of extract, transform, and load? Select every one that does.

Select all that apply.

Yes. Transform derives the attributes the dimensions carry.

Yes. Transform computes the facts at the declared grain.

Yes. Cleaning the data is part of turning it into the warehouse’s form.

Reading the data from the operational sources is the extract step.

Looking up surrogate keys from business identifiers is done as the rows are written: the load step.

2. A date dimension’s month_name column was filled with TO_CHAR(d, 'Month'). A report then filters on WHERE month_name = 'May' and finds no rows, although May has 31 days in the dimension. What went wrong?

The date dimension is generated, one row for every day, whether or not anyone ordered that day.

Yes. 'May' is not equal to the padded value, so every comparison fails. Writing the format as 'FMMonth' stores the name without padding.

The month number is a separate column; month_name holds text.

PostgreSQL compares whole strings, which is exactly why the padded value fails to match.

3. A nightly refresh may be run a second time after a failure. What in the chapter’s fact load makes that safe?

A surrogate key is new for every row inserted, so it would happily number a second copy of each fact.

Yes. Whatever the warehouse already holds is skipped, so a second run adds nothing, as the double refresh of the new customer’s order showed.

That would reload everything every night. The refresh is designed to load only what is new.

A schedule does not prevent a second run after a failure. The condition in the statement does.

4. The date dimension of stage S has a row for every day of 2026 and 2027, though orders were placed on far fewer days. Why?

The date dimension is not extracted from anywhere.

Yes. PostgreSQL’s generate_series produces the days, and the year, quarter, month, and day names are transformations of each one, whether or not anyone ordered that day.

A dimension has one row per member, here one per day, and many facts may refer to the same day.

A foreign key requires only that each date a fact refers to exists. Covering every day is a design choice, not a rule of the key.

Slowly Changing Dimensions

Read the section

Self-Check

1. Arkansas Valley Supply corrects its city in the operational customer table after the warehouse has loaded it. What does the next nightly refresh, as the chapter’s example writes it, do to the customer dimension?

The customer load only inserts. Its condition skips customer numbers already in the dimension.

Yes. The refresh adds new rows but never changes old ones. A changed member is what the types of slowly changing dimension handle.

Adding a row is type 2, which needs dates, a current flag, and a load written for it. The example’s load does none of this.

Nothing compares the two. The load finds the customer number present and skips it.

2. Prairie Garden Center moves on January 1, 2027, and the warehouse handles the move as type 2. What happens to the customer’s existing dimension row?

Yes. The facts from before the move still refer to it, so they stay in the region the customer was in when they were ordered.

That would move the old facts, just as type 1 does. The old row is kept for them.

Overwriting is type 1, which rewrites the history type 2 keeps.

A column for the previous value is type 3, which keeps one step of history.

3. After the type 2 change, the nightly fact load must find, for each order line, the customer dimension row that was valid on the order’s date. Which join condition does the chapter add?

Yes. The dates pick the version of the customer in effect when the order was placed, so a 2027 order refers to the new row.

That is right for an order placed today, but a reload of older orders would put them in the customer’s present region.

The newest row, like the current one, is wrong for the orders placed before the change.

valid_from is the day a version began. Most orders fall between a row’s two dates, not on its first.

4. Which statement about choosing how to handle a slowly changing dimension is right?

The choice is made attribute by attribute, according to the history the business needs of each.

Type 3 adds one column for the previous value. It keeps one step of history and no more.

Yes. Ask what history the business needs of each attribute before the first load, while that history can still be kept.

Which history matters is for the business to say, since it decides what the reports mean.

Multidimensional Queries

Read the section

Self-Check

1. An analyst restricts the sales facts to garden carts sold to Fayetteville region customers in 2026. Which operation is that?

Rolling up summarizes to a coarser level of a dimension, such as from quarters to years. No level changes here.

Drilling down breaks a total into finer levels. Nothing is broken down here.

A slice fixes one dimension at one value. This request sets conditions on three.

Yes. A dice selects a sub-cube with conditions on several dimensions at once, and in SQL it is a WHERE clause on dimension attributes.

2. ROLLUP and CUBE are shorthand for grouping sets. Which GROUPING SETS clause asks for the same groupings as GROUP BY ROLLUP (product_line, sales_region)?

That is only the cells, an ordinary GROUP BY on both columns. ROLLUP adds the subtotals and the total.

Yes. ROLLUP drops columns from the right, one at a time, down to the grand total, so it follows one hierarchy from coarse to fine.

That drops product_line first, which is ROLLUP (sales_region, product_line). The order of the columns in ROLLUP matters.

That gives the two sets of subtotals without the cells or the total, a grouping neither ROLLUP nor CUBE produces.

3. In a row of a ROLLUP result, sales_region is NULL. What does that NULL mean, and how can a query tell?

IS NULL cannot tell a subtotal’s NULL from a region that really is missing in the data.

Yes. The NULL means “all”, not unknown or not applicable, and GROUPING lets a report label its subtotals.

The NULL is how SQL marks the rolled-up column in a subtotal row. It is expected.

The WHERE clause runs before grouping, so it cannot remove subtotal rows; and they are rows the report asked for.

4. The history of stage S runs from January 2026 to March 2027. A report groups the facts by calendar_quarter alone. What goes wrong?

Each quarter number appears once, but the first quarter’s row is not one quarter.

Yes. A quarter means nothing without its year. Group by ROLLUP (calendar_year, calendar_quarter), the hierarchy from coarse to fine, and the quarters stay in their years.

A grouping column need not be a key. The query runs and returns a misleading total.

SUM over the facts never sees an empty day; the trouble is merging two years.
