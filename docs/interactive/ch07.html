The Procedure and Anomalies in a Poorly Designed Table

Read the sections

Self-Check

1. A tool crib keeps one flat table, with a row for each checkout: the tool’s number and description, the employee who took it, and the date. A new torque wrench arrives, and nobody has checked it out yet. Which anomaly keeps the crib from recording the new wrench and its description?

Nothing is being changed. The trouble is a fact that has no row to go on.

A deletion anomaly loses a fact when a row is removed. Nothing is being removed.

Yes. The wrench’s description can be recorded only on a checkout row, so it cannot be recorded until an unrelated fact, a checkout, exists.

A checkout row with no checkout records something that did not happen. The table has no place for a tool on its own, which is the anomaly.

2. The sales department keeps its orders in the flat order report, a row for each order line with the customer’s number and name and the product’s number and description. Which of these situations are symptoms of the report’s design? Select every one that is.

Select all that apply.

Yes. Two names for one number is the trace of a rename that missed some rows: an update anomaly that has already happened.

Yes. The description was stored only on that line, so removing the line removes the fact: a deletion anomaly.

Yes. The product’s description needs an order line to sit on: an insertion anomaly.

This is legitimate data, not an anomaly. An order may list a product on two lines, and each line is a fact of its own.

3. Step 4 of the normalization procedure names a table’s normal form. How is it done?

The sample shows where facts repeat, but the normal form is a condition on the dependencies, not a count of values.

Yes. The forms are nested, so the first one a table fails tells you which kind of repeated fact it holds, and which split step 5 must make.

The procedure tests from the first form up, since each form includes the ones below it.

A database does not know a table’s dependencies, so it cannot name the table’s normal form.

Functional Dependencies

Read the section

Self-Check

1. A hypothetical tool crib table holds these three rows:

Tool Description Bin
T-1 Torque wrench B4
T-2 Torque wrench B7
T-1 Torque wrench B4

Which functional dependencies do these rows refute? Select every one.

Select all that apply.

Each tool number appears with one description here, so the rows do not refute it.

Yes. “Torque wrench” appears with T-1 and with T-2, two values of the dependent for one value of the determinant. Reading a dependency backwards is a common mistake: two tools may share a description.

T-1 appears twice, both times in B4, so the rows agree with the dependency.

Yes. “Torque wrench” appears with B4 and with B7.

2. A sales clerk has kept a flat order table by hand for years. A query groups it by customer_number and keeps the groups with COUNT(DISTINCT customer_name) > 1, and it returns three customer numbers. What does that result show?

The business still gives each customer one name. The rows broke the rule; they did not repeal it.

Yes. A dependency is broken wherever one value of its determinant appears with two values of its dependent. In a table kept by hand, this query is the quickest way to find the damage.

That would be one name with several numbers, the dependency read backwards. The query found one number with several names.

Each of the three numbers appears with more than one name, which is exactly what the dependency forbids.

3. A hypothetical table records the steps of work orders: (work_order_number, step_number, work_center, center_manager, hours), with key (work_order_number, step_number). The rules are that each step of a work order is performed in one work center, and each work center has one manager. How does center_manager depend on the key?

A partial dependency leaves one column of a composite key. Here the work center depends on the whole key, since a work order has several steps in different centers.

Yes. The key decides the work center, and the work center decides its manager. The manager is repeated on every step performed in the center.

The manager is decided by the work center alone, whatever the work order or the step.

It does, through the chain from the key to the work center to the manager.

Normal Forms

Read the section

Self-Check

1. A query builds a report with one row per order and a column products that holds the order’s product numbers joined into one string, such as “HT-100, GC-300”. Why does such a column belong in a report and never in a stored table?

A text column holds commas like any other character. The trouble is what the value means, not how it is typed.

Yes. A list in one cell breaks first normal form. Read in a report, it is convenient; stored, it hides facts the database cannot reach.

The number of rows has nothing to do with a normal form.

The standard’s aggregate, LISTAGG, builds the same list, and the list would be just as wrong in a stored table.

2. In a functional dependency diagram, order_number and line_number together decide product_number. How is that drawn?

Two separate arrows would say that each column alone decides the product, which is false: every order has a line 1.

Yes. Only the two columns together decide the value, so the arrow starts from the outline that holds them both.

Each column keeps its own oval, and every dependency is drawn as an arrow.

Arrows run from the determinant to the columns it decides, not the other way.

3. The chapter states BCNF with candidate keys, and adds that, strictly, a determinant may also be a superkey. What is a superkey?

The number of columns does not make a superkey.

Yes. A candidate key with columns added to it still decides every column, so it is a superkey. The book states the rule with candidate keys because a determinant is taken to be as small as it can be.

The primary key is the candidate key chosen to identify rows. A superkey need not be chosen at all.

A key belongs to one table. A superkey is a set of a table’s own columns.

Decomposition

Read the section

Self-Check

1. A hypothetical lot table (lot_number, part_number, part_description, quantity_made) has key lot_number and fails third normal form through part_number → part_description. Which split repairs it?

Yes. The determinant and the column it decides move to a new table keyed by the determinant, and the determinant stays behind as a foreign key that refers to it.

With part_number gone, nothing says which part a lot made, and joining the two tables cannot give the lots back.

The new table’s key is the determinant of the dependency, part_number. Two parts may share a description.

Keeping the description in the lot table keeps the repeated fact and the transitive dependency the split was meant to remove.

2. The order report is decomposed into customer, customer_order, order_line, and product, and the dependencies are drawn with each table in its own outline. What in the drawing shows that each table is in Boyce-Codd normal form?

The tables have different numbers of columns, and the count says nothing about the dependencies.

Yes. A table whose only determinant is its key meets the condition of BCNF.

Every table still has its dependencies. What changed is where the arrows start.

Most columns, such as customer_name and quantity, are not part of a key, and need not be.

3. After the order report is decomposed, the transitive chain order_number → customer_number → customer_name is cut at its middle column. What is customer_number in the result?

With customer_number gone from the order’s table, nothing would say which customer placed an order.

Yes. The middle column of each chain becomes a foreign key in one table and the key of another, which is how the tables join back together.

It appears only where it is needed: as the key of customer and as the reference to it.

Normalization works with the natural columns. Surrogate keys are added by the mapping, not by the decomposition.

4. The inspection sheet was normalized under the rule that a lot is inspected once. Suppose instead that a failed lot may be reworked and inspected again. What changes?

Yes. The dependencies came from a business rule, and when the rule changes, they change. The book’s database anticipates this by giving each inspection its own surrogate key.

The rule of the business has changed, and the dependencies follow the rule.

First normal form concerns atomic values, which a second inspection does not change.

That would record something false about the lot. The design must change to fit the rule, not the other way round.

Normalization and Class Modeling

Read the section

Self-Check

1. A class model gives the class OrderLine an attribute orderDate. Which normal form does the mapped order_line table fail?

The order date is one value per row, so it is atomic.

Yes. The date depends on the order alone, part of the line’s key, so it is repeated on every line of the order. The repair belongs in the model: the attribute describes the whole, CustomerOrder, not its part.

Third normal form concerns a column that depends on another column outside the key. The date depends on part of the key.

Every line of an order has the order’s date, so the date describes the order, not the line.

Multivalued Dependencies and Fourth Normal Form

Read the section

Self-Check

1. A hypothetical table holds each machine’s certified operators and its maintenance tasks, a row for each combination. The multivalued dependency machine →→ operator holds. Which part of that statement goes beyond a machine simply having many operators?

That is a rule about operators, and the dependency does not state it.

Many operators per machine is only a one-to-many relationship. A multivalued dependency says something more.

Yes. Because the set does not depend on the task, every operator must be paired with every task, which is where the repetition comes from.

The arrow runs from the machine. An operator may be certified on several machines.

2. The table is split into machine_operator (machine, operator) and machine_task (machine, task). The two join on machine, which is a key of neither. Why is the split lossless all the same?

Whether a split loses nothing depends on the dependencies behind it, so it must be shown for each split.

The original table’s key is all three columns together.

Yes. A split on a multivalued dependency is lossless for this reason, not by the rule that governs a split on a functional dependency.

DISTINCT removes duplicate rows. It cannot remove a row that was never true.

Self-Check

1. One engineer normalizes HG Industries’ flat order report. Another maps the class model of customers, orders, order lines, and products to tables. How do their designs compare?

The two start from different places and meet at the same design, because both follow the same dependencies.

Yes. Normalizing a table that exists and mapping a sound class model are two routes to one design, and a normal form violation in a mapped table points back to a mistake in the model.

Each split follows a dependency that breaks a normal form, and the order report needs three splits, giving four tables.

A class whose attributes each describe its own object maps to tables already in Boyce-Codd normal form.

2. Which statements agree with the chapter? Select every one.

Select all that apply.

Yes. Each form names one kind of repetition and the dependencies that cause it.

Yes. A larger set that also determines every column is not a key, since a smaller one does the work.

Yes. The book names it and goes no further.

The arrow runs from the determinant to each column it determines.

Normalization works with the natural columns. Surrogate keys are a decision of the mapping.

3. The quality engineers like reading their inspection results as one sheet, a row per measurement with the part’s description and the inspector’s name. How should the database serve them?

Every copy is a place where the table can contradict itself, and an insertion or deletion anomaly cannot be avoided by care.

Yes. The sheet is a fine way to read the results, and a query produces it on demand while each fact stays stored once.

Two stored copies are two places to update, the problem normalization removes.

Splitting is done on a dependency, not on every column, and a split that drops the key from a table loses the link between its facts.
