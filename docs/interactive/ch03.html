Chapter 3 Self-Checks

Querying Tables

These questions follow the order of Chapter 3. Each of the first seven groups checks one or two sections of the chapter, and the last group reviews the whole chapter. The “Self-check” buttons in the chapter lead to these groups. Nothing you answer is recorded.

The SELECT Statement and Filtering Rows

Read the sections

Self-Check

1. A query looks up a customer with the condition WHERE customer_number = "C-1001". What happens?

They do not. A text value is written in single quotes, and double quotes mark a name.

Yes. Written 'C-1001', in single quotes, the value is text, and the query finds the customer.

The double quotes are not read as part of a value at all. They make C-1001 the name of a column.

Being a key does not change how a value must be written in a condition.

2. A query names only product_number and description after SELECT, and its condition is WHERE list_price < 125. What does it return?

The condition is allowed. The WHERE clause sees every column of the table.

Yes. The condition is evaluated on the whole row, whether or not the SELECT list names the column it tests.

The result has only the columns the SELECT list names. Testing a column does not add it to the result.

Showing a column and testing it are separate. The rows are still filtered by price.

3. Which product numbers does the condition product_number LIKE 'GC-_00' match? Select every one it does.

Select all that apply.

Yes. The _ stands for exactly one character, here the 3.

Yes. Any one character may stand where the _ is.

The pattern has exactly six characters, and the _ matches one character only. This number has seven.

The pattern begins with GC-, which must match exactly.

NULL and Three-Valued Logic

Read the section

Self-Check

1. A work order is still in process, so its completed_on is NULL. Its due_on is a date in the past. What is the value of the condition completed_on > due_on for this work order?

The work order is overdue, but this condition compares the completion date, which is unknown.

NULL is not treated as zero or as an empty value. A comparison with NULL has a third value.

Yes. A comparison in which either side is NULL is neither true nor false; it is unknown. A WHERE clause discards the row, just as it would discard a false one.

Comparing with NULL is allowed. It gives an answer, just not true or false.

2. Work order WO-7008 is open, so its completed_on is NULL, and it was due on March 13, 2026. What is the value of completed_on > due_on OR due_on < DATE '2026-03-20' for it?

Yes. The first part is unknown and the second is true, and true OR anything is true, whatever the unknown turns out to be.

An unknown part makes an OR unknown only when the other part is not true. Here the other part is true.

A missing completion date makes the first comparison unknown, not false, and the second part is true anyway.

Combining unknown with OR is allowed, and the truth table of OR gives its value.

3. The query for the work orders that are late as of March 20, 2026 writes the date DATE '2026-03-20' into its condition. What should change if the plant manager wants the same list every morning?

With the date written in, the query answers the question as of March 20 only.

Yes. The open work orders due before today are late today, so the comparison must move with the day.

That condition misses every open work order, since it is unknown whenever completed_on is NULL.

Sorting changes the order of the rows, not which rows count as late.

Sorting, Limiting, and Expressions

Read the sections

Self-Check

1. A query ends with ORDER BY warehouse_fk, quantity_on_hand DESC. In what order does it list the stock levels?

DESC applies only to the column it follows. Each column is sorted on its own terms.

Yes. The first column sorts the rows, the second breaks the ties within it, and only the second is descending.

The columns sort in the order they are named, so the warehouse comes first.

The second column breaks the ties of the first, so the quantities within each warehouse are sorted.

2. For a work order still in process, completed_on is NULL. What does the expression completed_on - released_on give for it, and what does COALESCE(completed_on, DATE '2026-03-20') - released_on give?

NULL is not zero, so the first expression is not zero.

Yes. Any arithmetic with a NULL operand gives NULL. COALESCE returns the first of its arguments that is not NULL, so it substitutes March 20 for the missing date.

Arithmetic with NULL is allowed; it gives NULL.

COALESCE replaces the NULL before the subtraction, so the second expression has a value.

3. Two orders have no requested ship date. A query ends with ORDER BY requested_ship_date. Where does PostgreSQL put those two orders?

PostgreSQL does the opposite in ascending order.

Yes. They come last in ascending order and first in descending order. The SQL standard leaves the choice to each database, so writing NULLS FIRST or NULLS LAST makes the query’s meaning plain anywhere.

Sorting never removes rows. Only WHERE, a join condition, or LIMIT can do that.

The two orders do move as a block to one end; only their order relative to each other is left to any further ORDER BY columns.

Inner Joins

Read the section

Self-Check

1. We evaluate a join by hand on three customers and the four orders that two of them placed. How many pairs does the cross product hold, before the join condition is applied?

Four is the number of pairs the join condition keeps, one for each order. The cross product comes first.

The cross product multiplies the row counts; it does not add them.

Yes. Every one of the 3 customers is paired with every one of the 4 orders, \(3 \times 4 = 12\), and the join condition then keeps the pairs whose keys match.

Every customer appears in the cross product, but each is paired with every order.

2. A query joins product, order_line, customer_order, and customer, one JOIN at a time. How many join conditions does it need?

Each JOIN adds one table and the condition that connects it to a table already joined.

Yes. A join of four tables needs three conditions, one for each foreign key along the path from product to customer.

The first table needs no condition; each table joined after it needs one.

Only tables connected by a foreign key are matched. Each condition follows one foreign key line of the schema.

3. A join can be written with both tables in FROM, separated by a comma, and the join condition in WHERE, or with JOIN and ON. Why does the book use the JOIN form? Select every reason it gives.

Select all that apply.

Yes. The conditions that connect tables stand apart from the conditions that filter rows.

Yes. A left join needs ON to say what counts as a match.

The two forms mean the same thing and return the same rows.

The database never actually builds the cross product, in either form. The cross product is how to think about a join.

Outer Joins

Read the section

Self-Check

1. A warehouse takes a physical count of its stock and wants to compare it with the stock levels on record. Either list may hold products that the other lacks. Which join suits the comparison?

An inner join keeps only the products in both lists, which hides exactly the differences the comparison is for.

This keeps every counted product, but a stock level that the count missed is left out.

Yes. A FULL JOIN keeps the unmatched rows of both tables, padded with NULL, so a product missing from either list appears.

A right join keeps every row of the table named after it, so it misses the counted products with no stock level on record.

2. Customer 8, Northgate Hardware, has placed no orders. In the result of customer AS c LEFT JOIN customer_order AS o ON o.customer_fk = c.customer_pk, what does Northgate Hardware’s row hold?

That is what an inner join does. A left join adds back the unmatched rows of its left-hand table.

Yes. The outer join supplies the NULLs; the customer’s own data comes from its table as before. Testing one of those NULL columns is how a left join finds the customers with no orders.

The left join pairs a row only with rows that satisfy the join condition, and none does.

Rows that do not match are not paired at all; the customer appears once, padded with NULL.

3. A report must list every warehouse, with its stock levels where it has any. Which FROM clauses keep a warehouse that has no stock levels?

Select all that apply.

Yes. The table named before LEFT JOIN is the one whose rows are all kept.

This keeps every stock level, but a warehouse with none matches no stock level and is left out.

An inner join returns only matched rows.

Yes. A right join keeps every row of the table named after it, here warehouse, so it is the left join above written the other way round. The book writes every outer join as a left join, which reads in the order of the request.

Subqueries

Read the section

Self-Check

1. A query keeps the products for which EXISTS (SELECT * FROM distribution.stock_level AS s WHERE s.product_fk = p.product_pk AND s.quantity_on_hand <= s.reorder_point) holds. Which statements about the EXISTS test are true? Select every one that is.

Select all that apply.

Yes. EXISTS tests only whether a row exists, so it is never unknown.

Yes. The select list of an EXISTS subquery does not matter; SELECT * is only the convention.

It refers to p.product_pk, the outer row, so it is read as being run once for each product.

The outer query reads the product table, and the test is true or false once for each product, so each appears at most once.

2. In a subquery, a column is named without its table’s alias, and the subquery’s own table has no column of that name, though the outer query’s table does. What happens?

It would refuse a qualified name, such as o.customer_pk. An unqualified name is looked up further out.

Yes. The query runs and gives a wrong answer rather than a message. That is why every column in a subquery should be named with its table’s alias.

The name is resolved to a real column, just not the one intended.

It returns rows, from the outer row’s own column.

3. A query keeps the products priced above one product’s price, looked up by a subquery:

WHERE list_price > (SELECT list_price
                    FROM distribution.product
                    WHERE product_number = 'HT-900')

No product has the number HT-900. What does the query return?

The subquery does have a value; it is just not a price.

Yes. A subquery used as a single value returns NULL when it finds no row. Had it found several rows, PostgreSQL would have stopped with an error instead. Looking the product up by its alternate key guarantees at most one row.

PostgreSQL stops with an error only when such a subquery returns more than one row.

Nothing in the query compares the products with one another.

Set Operations and Common Table Expressions

Read the sections

Self-Check

1. A UNION of the customers’ cities and states and the warehouses’ cities and states ends with ORDER BY state, city. What does the ORDER BY sort?

The ORDER BY follows the second query, but it does not belong to it.

Yes. An ORDER BY at the end of a set operation sorts the result that the operation produces.

The union is one result, and it is sorted as one.

A union is a result like any other, and an ORDER BY sorts it.

2. Which statement about a common table expression that does not refer to itself is true?

A CTE exists only while its statement runs.

It could be written as a subquery in the FROM clause instead.

Yes. What it adds is readability: each step can be named for what it means, and run and checked on its own.

A CTE comes first, introduced by WITH; the statement that uses it follows.

Review of the Whole Chapter

Read the chapter summary

Self-Check

1. A request reads “the number, description, and list price of each product under $125, cheapest first”. Which clauses does its query need besides SELECT and FROM?

“Cheapest first” says in what order, which is a clause of its own.

Yes. “Under $125” says which rows, and “cheapest first” says in what order. Reading a request clause by clause tells you which clauses its query needs before you write any of them.

“Under $125” is a condition on each row, not a count of rows.

Nothing in the request divides the products into groups.

2. A query finds the products that have never been ordered by joining product AS p LEFT JOIN order_line AS l ON l.product_fk = p.product_pk and keeping the rows where a column is NULL. Which test should it use?

Yes. A real order line always has a primary key, so a NULL there can come only from the left join’s padding.

Every row’s product columns come from the product table itself, and its key is never NULL, so this keeps no rows.

This keeps the products that matched an order line: those that have been ordered.

A product’s own columns say nothing about whether it matched an order line.

The test must use a column that cannot be NULL in a matched row. Otherwise a product that was ordered could look unordered.

3. Before running a new query, why evaluate it by hand on a few rows?

The database knows nothing of our prediction.

Yes. Write down what each step produces, then run the query; its result must match. The habit also builds the understanding that makes a long query readable.

It is slower. Its value is the check it gives, not speed.

Conditions with NULL, AND and OR, and LIMIT with ties all reward the same check.
