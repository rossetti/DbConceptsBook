Chapter 9 Self-Checks

Views, Transactions, and Concurrency

These questions follow the order of Chapter 9. Each of the first four groups checks one section of the chapter, and the last group reviews the whole chapter. The “Self-check” buttons in the chapter lead to these groups. Nothing you answer is recorded.

Views

Read the section

Self-Check

1. The view order_report joins orders, customers, order lines, and products. After it is created, one product’s description is changed with an UPDATE of product. What does the next query of the view show for that product’s lines?

Yes. A view stores no rows. Each query that uses it runs the view’s query against the tables as they are at that moment, so the one changed row shows everywhere.

That would be true of a stored copy. A view is a named query, not a copy of its result.

The view holds no history; every line reads the one current row of product.

The tables behind a view are changed as usual. The view simply reads them as they are.

2. Which of these views does PostgreSQL make updatable automatically? Select every one.

Select all that apply.

Yes. It selects from a single table, and each of its rows comes from one row of customer.

Yes. Choosing some of a single table’s columns keeps each view row tied to one table row.

LIMIT is among the clauses that keep PostgreSQL from making a view updatable automatically.

A row of an aggregate comes from many rows, so the database could not tell which row a change should reach.

DISTINCT merges rows, so a view row no longer comes from one table row.

3. The view oklahoma_customer shows the customers WHERE state = 'OK' and was created WITH CHECK OPTION. What does the clause do?

The clause knows nothing of valid states. It compares a row with the view’s own condition.

Yes. Without it, a clerk could add through the view a row that the view itself would never show.

A view with the clause still stores no rows. A view that stores its result is a materialized view.

The clause does not make a view updatable. It limits the changes allowed through a view that already is.

4. True or False: because a view is defined in advance, a query of the view runs much faster than the same query written out with the view’s joins.

A view stores no rows, so its query still runs every time. Storing the result for speed is what a materialized view does, at the price of being current only when refreshed.

Correct. PostgreSQL merges the view’s query into the query that uses it, so the two cost about the same. A materialized view trades currency for speed and is brought up to date only by REFRESH MATERIALIZED VIEW.

Transactions and the ACID Properties

Read the section

Self-Check

1. In PostgreSQL, a foreign key with NO ACTION is declared DEFERRABLE INITIALLY DEFERRED. Inside one transaction, a statement leaves a row that refers to nothing, and a later statement repairs the reference before COMMIT. What happens?

That is how a key that is not deferred behaves. A deferred key waits.

Yes. Deferring the check lets a transaction pass through an inconsistent state on its way to a consistent one.

The deferred check looks at the rows as they are at COMMIT, not at the states the transaction passed through.

A RESTRICT check is never deferred. It is the NO ACTION key that can wait until COMMIT.

2. A transaction runs these steps in PostgreSQL:

BEGIN;
UPDATE stock_level ... ;   -- succeeds
SAVEPOINT before_carts;
UPDATE stock_level ... ;   -- refused
ROLLBACK TO SAVEPOINT before_carts;
COMMIT;

What is committed?

Yes. ROLLBACK TO SAVEPOINT undoes only the work after the savepoint, here the refused statement, and the first update stays in the transaction.

The savepoint marks a point to return to, and rolling back to it keeps the work done before it.

The second update was refused, and it made no change to keep.

It ends nothing. Only COMMIT or ROLLBACK ends the transaction.

3. Against which events does durability protect a transaction whose COMMIT has returned? Select every one.

Select all that apply.

Yes. PostgreSQL wrote the change to its write-ahead log before reporting the commit, and replays the log after a crash.

Yes. A crash of the machine is recovered from the log in the same way.

Durability keeps committed changes, mistaken ones included. Recovering the deleted rows takes a backup.

The log is on a disk too. A failed disk or a lost machine calls for a backup kept elsewhere.

4. True or False: in DataGrip or DBeaver with the console in auto-commit, a DELETE typed by mistake can be undone with ROLLBACK, provided no other statement has run since.

In auto-commit, each statement runs in its own transaction and is committed at once, so there is nothing left to roll back.

Correct. The DELETE is permanent the moment it runs. To experiment safely, type BEGIN first and end with ROLLBACK.

Concurrency and Isolation Levels

Read the section

Self-Check

1. Two clerks, each in a transaction, insert a customer with the same customer number, a UNIQUE column. Clerk A’s insert runs first, and A has not yet committed. What happens to clerk B’s insert in PostgreSQL?

A’s row is not committed and may yet be rolled back, so the database cannot yet say whether B’s row is a duplicate.

Yes. Two inserts of the same value of a UNIQUE column wait for each other, as two changes of the same row do.

B cannot read A’s row, but the constraint must still account for it, so B waits.

A UNIQUE constraint never lets two committed rows share a value, and nothing is removed for you.

2. Transaction A runs in PostgreSQL at REPEATABLE READ. It totals the carts in stock; transaction B then changes one stock level and commits; A totals the carts again and then tries to change the same stock level. What happens?

That is READ COMMITTED, where each statement sees the data committed when the statement began.

Yes. A sees the database as it was when its first statement ran, and it may not change a row that another transaction changed after that. A program at this level must be written to retry.

Overwriting a change A never saw is the lost update. REPEATABLE READ refuses it instead.

B has already committed. The refusal comes because the row changed after A’s first statement.

3. At READ COMMITTED, a planner’s transaction runs one long SELECT SUM(quantity_on_hand) over every stock level. While the query is running, a clerk’s change to one stock level commits. What does the planner’s sum include?

Yes. At READ COMMITTED each statement sees the data as committed when the statement began, so one statement’s result is consistent with itself.

A statement’s view of the data is fixed when the statement begins.

The whole statement sees the data as it was committed when the statement began.

A commit by another transaction does not cancel a query. The query simply reads the data its view calls for.

4. Transaction A has updated a stock level and has not yet committed. Transaction B, at READ COMMITTED, runs an ordinary SELECT of the same row. What does B get in PostgreSQL?

Reading a change that is not committed is a dirty read, and B, at READ COMMITTED, reads only committed data.

Yes. PostgreSQL keeps several versions of a changed row, and a reader sees the version its snapshot calls for, so an ordinary read never waits for a write.

A’s lock makes another change of the row wait, as it does a read that locks, such as SELECT ... FOR UPDATE. An ordinary read does not wait.

Reading a row that another transaction is changing is allowed; the question is only which version is read.

Security and Privileges

Read the section

Self-Check

1. A program prints a weekly report from the quality schema and changes nothing. Which practices does the chapter call for? Select every one.

Select all that apply.

Yes. A program connects as a role whose privileges match its job, so a mistake in it cannot change data.

Yes. No password belongs in a script or in code kept under version control.

No program should connect as the owner or as a superuser; a mistake would then have every privilege.

Source code is shared and kept under version control, so a password in it is given to everyone who reads the code.

2. The role hg_sales is granted SELECT on the view production.part_catalog, but nobody has granted it anything on the schema production. A clerk acting as hg_sales queries the view. What happens?

A table or view can be reached only through its schema, which needs a privilege of its own.

Yes. USAGE on a schema is needed to reach the objects in it at all, which is why the sales role is granted USAGE on production along with the view.

A missing privilege refuses the statement; it never silently empties the result.

Views are granted like tables; granting a view and not its table is how the chapter hides the standard cost.

3. Why does each sales clerk get a login role of their own, made a member of the group role hg_sales, rather than everyone logging in as one shared role?

A login role can hold privileges. The group is a matter of management, not of what roles can do.

Yes. Granting or revoking a privilege on the group changes it for every member, and the database still knows who did what.

A new role has no privileges beyond those granted to everyone. NOLOGIN means only that nobody logs in as it.

A shared login hides who opened each session, and its password must be given to everyone who uses it.

Review of the Whole Chapter

Read the chapter summary

Self-Check

1. HG Industries keeps at least 30 carts of one product across its two warehouses. A planner’s program checks the total and then takes carts from one warehouse, while another planner may do the same at the other warehouse. At which isolation level should the program’s transaction run in PostgreSQL?

The default allows both planners to read the same total and both changes to commit.

The two planners change different rows, so REPEATABLE READ finds nothing to refuse: a write skew.

Yes. PostgreSQL tracks what each transaction read and refuses a commit that no one-at-a-time order could produce. The program must retry a transaction that fails this way.

A short transaction makes the overlap less likely, but the same schedule can still occur, and both changes commit.

2. Transaction A has changed stock level 1 and now wants stock level 3, while transaction B has changed stock level 3 and now wants stock level 1. What does PostgreSQL do?

Neither can proceed, but the database does not leave them waiting.

Yes. Neither transaction can proceed, so the database breaks the deadlock by cancelling one, and the program that receives the error tries its work again.

Cancelling one is enough to let the other go on.

Each transaction holds its lock on the row it changed until it ends, so the second change of each must wait.

3. Which habits does the chapter recommend for an engineer who writes reports and programs against a shared database? Select every one.

Select all that apply.

Yes. A long transaction makes others wait for the rows it has changed.

Yes. Only that level refuses a write skew.

Yes. At those levels PostgreSQL refuses a change it cannot make safely, and the work must be tried again.

A program should connect as a role that may do only what its job needs, and never as the owner or a superuser.

SERIALIZABLE is the level whose transactions may fail and need a retry, sometimes even when they would have done no harm.
