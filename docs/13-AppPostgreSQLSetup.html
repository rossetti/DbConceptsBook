Appendix A — Installing PostgreSQL and Its Tools

This appendix sets up what the book’s examples need: a PostgreSQL server on your own computer, DataGrip or DBeaver to work with it, and the book’s database loaded into it. It also introduces psql and pgAdmin, which come with PostgreSQL, so that you recognize them. The steps take under an hour, most of it waiting for downloads.

The book’s results were produced with PostgreSQL 18. Later releases give the same query results, but the order of the rows in a result without ORDER BY, what a result shows of the database’s own catalog, and the wording of an error message can differ from one release to the next. PostgreSQL publishes a new major release about once a year, and supports each for five years. Install the current one unless your course or employer asks for another.

A.1 Installing the PostgreSQL server

PostgreSQL runs as a server, a program that starts with your computer and waits for connections (Section 1.3). Installing it creates the server, a first database named postgres, and a first user, a superuser who may do anything. The installers differ by operating system.

  • macOS. Postgres.app (postgresapp.com) is the simplest: move it to the Applications folder, open it, and choose Initialize. The server then runs whenever the app does, and its first user has your macOS login name and no password. To use psql and the other command-line tools from a terminal, add them to your path once, as the app’s site describes:

    sudo mkdir -p /etc/paths.d &&
echo /Applications/Postgres.app/Contents/Versions/latest/bin |
sudo tee /etc/paths.d/postgresapp

    Homebrew (brew install postgresql@18) and the EDB installer below also work on macOS.

  • Windows. Download the interactive installer by EDB from the Windows page of postgresql.org/download. Keep the default components (the server, pgAdmin 4, and the command-line tools); Stack Builder is not needed. The installer asks for a password for the superuser, named postgres: choose one you will remember, since every tool asks for it. Keep the default port,

    1. The server then starts with Windows. The installer does not put the command-line tools on your path: search the Start menu for Edit environment variables for your account, select Path, choose Edit, then New, enter the folder C:\Program Files\PostgreSQL\18\bin, choose OK in both windows, and open a new terminal. A terminal inside an application that was already open, such as IntelliJ IDEA’s, keeps the old path until the application restarts. The Start menu’s SQL Shell (psql) also opens psql, and asks for each connection setting in turn, showing its default in brackets; press Enter to accept it.

  • Linux. Install the server from your distribution’s packages, or from the PostgreSQL project’s own repository for a newer release, as the Linux page of postgresql.org/download explains. The superuser is postgres, reached with sudo -u postgres psql.

To check the installation, open a terminal and ask psql for its version:

psql --version

If the command is not found, the tools are not on your path; add them as the step for your system describes. The rest of this appendix assumes the server runs on your own computer (localhost) at port 5432.

The superuser is all you need for the book: you create and load your own databases on your own computer. On a shared server, you would instead be given a role with only the privileges your work needs, as Section 9.4 describes.

A.2 Connecting with DataGrip

DataGrip, by JetBrains, is a database tool for many DBMSs, and the one this book’s steps assume. It is free for non-commercial use, including learning, from version 2025.2.4, and free to students with a JetBrains student license; choose Non-commercial use when it first starts.

To connect to your server:

  1. Choose File, New, Data Source, PostgreSQL.
  2. Enter the host localhost, the port 5432, your user (your login name with Postgres.app, postgres otherwise) and its password, and the database postgres for now.
  3. If DataGrip offers to download the PostgreSQL driver, accept.
  4. Choose Test Connection, then OK.

DataGrip lists the new data source in its Database Explorer. By default it shows only some of a database’s schemas; open the data source’s properties and, on its Schemas tab, select All schemas, or the book’s schemas will seem to be missing after you load them.

Two ways of running SQL cover everything the book asks. A query console (right-click the data source, New, Query Console) holds statements you type; place the cursor in one and press Ctrl+Enter (Cmd+Enter on macOS) to run it. A script file (File, Open, then choose the data source to run it against) runs whole: right-click in it and choose Run. The book’s load files are script files.

A.3 Connecting with DBeaver

DBeaver is a database tool for many DBMSs whose Community Edition is free and open source (dbeaver.io). The book’s steps work in it as well as in DataGrip.

  1. Choose Database, New Database Connection, PostgreSQL.
  2. Enter the host localhost, the port 5432, the database postgres, and your user and password, as for DataGrip.
  3. On the PostgreSQL tab, select Show all databases, so that the databases you create later appear.
  4. Accept the offer to download the driver, choose Test Connection, then Finish.

Open an SQL editor on the connection (SQL Editor, New SQL script). Press Ctrl+Enter to run the statement under the cursor, and Alt+X to run the whole script. The book’s load files are run with Alt+X.

A.4 psql and pgAdmin

Two tools come with PostgreSQL itself. The book does not build on either, but you will meet both.

psql is PostgreSQL’s command-line client. It connects to a database, runs SQL typed at its prompt or read from a file, and adds its own commands, which begin with a backslash. Run from a terminal, psql -d dbconcepts connects to the book’s database; \dn lists its schemas, \dt distribution.* the tables of one schema, \d distribution.customer one table’s columns, keys, and constraints, \i file.sql runs a script, and \q quits. On Windows, psql connects as your Windows login name, which is not a role on the server, so name the superuser, psql -U postgres -d dbconcepts, and give the password you chose at installation. In the Command Prompt, psql may also warn that the console code page differs from the Windows code page. The warning concerns only how accented letters show in that window, such as those in some names of the public sample databases, and DataGrip and DBeaver are not affected. On Linux, run psql as the superuser, sudo -u postgres psql -d dbconcepts. Listing the schemas of the book’s database, loaded through stage S, gives:

         List of schemas
     Name     |       Owner
--------------+-------------------
 distribution | rossetti
 production   | rossetti
 public       | pg_database_owner
 quality      | rossetti
 sales        | rossetti
(5 rows)

The owner is the user who loaded the database, here the author’s login name. psql is the quickest way to run a script from a terminal, and the book’s own tooling uses it for that.

pgAdmin is a graphical administration tool, installed with the Windows installer and available separately for macOS and Linux. It shows a server’s databases, schemas, tables, roles, and settings, and has a query tool. It suits administration (Section 1.3); for the work of this book, DataGrip or DBeaver is the better fit.

A.5 Creating the book’s databases

The book’s database lives in a database of its own, named dbconcepts. Create it once, connected to the postgres database, in a DataGrip or DBeaver console:

CREATE DATABASE dbconcepts;

or from a terminal with createdb dbconcepts (on Windows, createdb -U postgres dbconcepts). Then change your data source to the dbconcepts database (in DataGrip, edit the data source’s Database field; in DBeaver, select it under the connection) and check the connection by running the companion script code/sql/setup/check-connection.sql. It reports the server’s version and which database and user you are connected as; its second result should read:

 current_database | current_user
------------------+--------------
 dbconcepts       | rossetti
(1 row)

with your own user name in place of the author’s. Now load the database: open code/sql/load/through-s.sql, from the book’s companion code (https://github.com/rossetti/DbConceptsBookCode), and run it as a script. It builds every schema through the last stage in a few seconds. Section C.2 explains the stages and how to load the database as it stands at any one of them, which is how you reproduce a chapter’s examples exactly.

Millbrook Transit, the exercise database of Section C.10, goes in a database of its own: create dbconcepts_transit as above and run code/sql/transit/t-schema.sql and then code/sql/transit/t-data.sql. The public sample databases, next, have a loader of their own.

A.6 Loading public sample databases

The public sample databases of Section C.11 are not distributed with the book. The companion code’s code/sql/public/ holds what is needed to fetch and load them: manifest.tsv, which gives each file’s address at a fixed release or commit of its source, its size, its license, and its SHA-256 checksum; load-public.sh, which does the work; and practical-schema.sql, which defines the tables for the Practical SQL files.

On macOS or Linux, or in Git Bash on Windows, with PostgreSQL running and psql on the path, run the loader with the database’s name. In Git Bash, first name the superuser and its password, so that each of the loader’s psql commands can connect:

export PGUSER=postgres
export PGPASSWORD='your-password'

The two settings last until the window closes. Do not save the password in a script or in any file you share. Then run:

code/sql/public/load-public.sh chinook
code/sql/public/load-public.sh northwind
code/sql/public/load-public.sh practical
code/sql/public/load-public.sh employees

Each command downloads the files once, into ~/.cache/dbconcepts-public, refuses any file whose checksum differs from the manifest’s, creates the database dbconcepts_<name>, and loads it. The employees database downloads about 172 MB and takes a minute or so to load; the others take seconds. A second argument names a different database, and --replace drops and rebuilds a database that exists; without it, the loader stops rather than overwrite anything.

Without a shell, the same can be done by hand. Create the database in DataGrip or DBeaver, download each file listed for it in manifest.tsv, and run it: Chinook’s script after deleting its first lines, which create and connect to a database of its own; Northwind’s as it is; for Practical SQL, practical-schema.sql followed by an import of each CSV file into its table (Section 8.5); and for employees, the schema script employees.sql, less its database lines, followed by the eight load_*.dump files after removing the MySQL backquotes (`) they contain. The loader’s comments give each step exactly.
