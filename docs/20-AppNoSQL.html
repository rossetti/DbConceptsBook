Appendix H — NoSQL and Other Data Stores

This book teaches the relational model because it holds most of the data an industrial engineer works with: orders, parts, routings, inspections, and the results of studies. It is not the only way to store data, however, and you will meet others, in a plant’s historian, in a supplier’s web service, or in a product team’s application. This appendix describes the databases grouped under the name NoSQL, the trade-offs they make against the relational model, and how PostgreSQL itself stores and queries JSON documents, so that you can try the ideas on the server you already have.

Recall from Section 2.7 that two questions separate one way of organizing data from another: where the description of the data lives, and how one record is connected to another. Those two questions run through the whole appendix.

H.1 Why NoSQL databases exist

A relational database was designed to run on one server and to keep one copy of each fact, checked against the rules in its catalog on every change. That design suits most business and plant data, and it still does. In the 2000s, however, companies running large web services met three needs it served poorly. Their data no longer fit on one machine, so it had to be spread over many machines and copied for safety. The structure of their records changed every few weeks, as the applications that wrote them changed. And much of their data arrived already shaped as documents, from browsers, phones, and other services.

The databases built for those needs came to be called NoSQL, usually read “not only SQL” (Sadalage and Fowler 2012). The name describes a family, not a rule: several NoSQL databases now accept a query language that looks much like SQL, and relational databases, PostgreSQL among them, have taken on features of NoSQL ones. What the family shares is a different answer to the two questions of Section 2.7. A NoSQL database usually keeps the description of its data in the records or in the programs, not in a catalog, and it connects records by nesting one inside another, or not at all, more often than by keys.

H.2 The four families

NoSQL databases fall into four families, distinguished by what they store and how a program finds it. Table H.1 summarizes them, with a use for each in a company like HG Industries.

A key-value store is the simplest: it stores a value under a key and returns the value when given the key. The value may be a number, a string, or a document, and the store does not look inside it. That simplicity makes it very fast, which is why it often sits in front of another database, holding the answers to frequent questions. For example, a dashboard on the plant floor that shows each machine’s current state reads one value per machine number, many times a second.

A document database stores each record as a JSON document, as Listing 2.5 showed, and groups documents of one kind into a collection, its counterpart of a table. Unlike a key-value store, it looks inside the documents: a query can ask for every order whose lines include a GC-300. Documents in one collection need not have the same fields. Thus, a document database suits records whose structure varies, such as test records in which a hand truck’s inspection measures different characteristics than a garden cart’s.

A wide-column store holds rows that may have very many columns, grouped by a key that decides which machine stores them. It is built for writing enormous numbers of rows quickly and reading them back by key and range. Sensor readings fit that pattern: each reading is written once, never changed, and read back by machine and time.

A graph database stores nodes, such as suppliers, parts, and products, and the relationships between them as data in their own right. Its queries follow relationships: which products depend, through any number of tiers, on one supplier’s plant. A relational database answers the same question with a recursive query (Section 4.6); a graph database makes following a path its basic operation, which pays off when the paths are long and the questions are about the paths themselves.

H.2.1 Time-series databases and plant historians

The non-relational data you are most likely to meet in a plant is neither of these four. A time-series database records the value of a measurement at each moment: a spindle’s speed, an oven’s temperature, a line’s count of finished units. In manufacturing, the usual one is a plant historian, such as the AVEVA PI System, which collects thousands of such measurements, called tags, from the plant’s controllers, many times a second, and keeps years of them. Other time-series databases include InfluxDB and TimescaleDB, the latter an extension of PostgreSQL.

A historian answers questions about one tag over a span of time well, such as the average oven temperature during each shift. It does not hold orders, parts, or work orders, so the questions an industrial engineer asks usually combine the two: the temperatures during the runs of one lot that failed inspection. The usual design summarizes the readings (an average, a minimum, and a maximum for each tag over each hour or each run) and loads the summaries into a relational database, where they join the rest of the plant’s data. That is the extract, transform, and load of Section 11.3, and the summaries are often the input data of the simulation models of Section 12.1.

H.3 The trade-offs

Each family gives up something the relational model provides in return for something it does not. This section names the four trade-offs that matter most when you choose.

H.3.1 Schema on write and schema on read

A relational database applies its schema when data is written. Every row is checked against the catalog of Section 2.5 before it is stored, and a row that does not fit is refused. This is called schema on write. A document database usually applies no schema when data is written: it stores whatever document it is given, and the program that reads a document decides what its fields mean. This is called schema on read.

Schema on read lets the structure change without redesigning the database, and it lets one collection hold records of different shapes. Its cost is that every program that reads the data must cope with every shape that has ever been written, including the mistakes. Section H.4 shows a document with a misspelled field being accepted, and a query answering wrongly as a result. Many document databases now let a designer declare rules that documents must obey, which moves them part of the way back to schema on write.

H.3.2 Nesting is denormalization

A document that nests an order’s lines and copies its customer’s and products’ facts is a table that has not been normalized. Recall from Section 7.2 that such a table suffers anomalies, and the order document of Listing 2.5 suffers them all: a product’s description is stored in every order that includes it, a product that has never been ordered has nowhere to be recorded, and removing a customer’s only order removes the only record of the customer.

A designer of documents therefore decides, for each connection, whether to nest or to refer. The class model of Chapter 5 gives a good rule. Nest a composition, whose parts belong to one whole and are created and removed with it (Section 6.3.6): an order’s lines belong in the order’s document. Refer, by key, to anything shared: a customer and a product are shared by many orders, so each belongs in a document of its own, and the order holds its customer number and each line’s product number. A document database that follows this rule copies only what never changes after it is written, such as the price on an order line.

H.3.3 Consistency across copies

A NoSQL database spread over many machines keeps several copies of each record, so that losing a machine loses nothing. Keeping every copy identical at every moment would mean that each change waits for every machine, and that a change is refused whenever the machines cannot reach one another. Many NoSQL databases choose instead to accept a change at one copy and pass it to the others shortly afterward. This is called eventual consistency: for a short time, a read from another copy may return the value from before the change.

Compare the transactions of Section 9.2, in which a change is complete and visible to all, or not made at all. For a dashboard, a value a second old does no harm; for the quantity on hand of a part that two planners are allocating, it does. Most NoSQL databases let a program ask for stronger consistency on the operations that need it, at the cost of speed.

H.3.4 Questions nobody planned for

A relational database answers any question its data can answer: a new question is a new query, joining whatever tables it needs. NoSQL databases are designed the other way round, around the questions known in advance. A key-value store finds a record only by its key, a wide-column store by its key and range, and a document database most easily by the fields of one collection; combining collections is often left to the program. Thus, the designer of a NoSQL database starts from the questions and shapes the records to answer them, while the designer of a relational database starts from the business, as Chapter 5 does, and lets the questions come later. For the data of an industrial engineer, whose next question is rarely the last one, that difference usually decides the matter.

H.4 Documents in PostgreSQL

PostgreSQL stores JSON documents in a column of type JSONB, a binary form of JSON that it can search and index, and it provides operators to reach inside them. This lets one database hold tables and documents side by side. The type and its operators are PostgreSQL’s own; the SQL standard defines functions for JSON since 2016, and PostgreSQL implements some of them, but other systems store and query JSON differently.

Let’s store the twelve orders of stage D5 as documents. The table has a key, the order number, and one column for the document; the database checks the key and that the document is well-formed JSON, and nothing more.

CREATE TABLE distribution.order_document (
    order_number VARCHAR(10) PRIMARY KEY,
    document     JSONB NOT NULL
);

The next statement builds a document for each order from the relational tables, in the form of Listing 2.5. The function jsonb_build_object builds a document from pairs of a field name and a value, and jsonb_agg gathers the documents of an order’s lines into a list.

INSERT INTO distribution.order_document
SELECT o.order_number,
       jsonb_build_object(
         'order_number', o.order_number,
         'order_date', o.order_date,
         'customer', jsonb_build_object(
             'customer_number', c.customer_number,
             'name', c.name,
             'city', c.city,
             'state', c.state),
         'lines', (
             SELECT jsonb_agg(jsonb_build_object(
                        'line_number', l.line_number,
                        'product_number', p.product_number,
                        'description', p.description,
                        'quantity', l.quantity,
                        'unit_price', l.unit_price)
                      ORDER BY l.line_number)
             FROM distribution.order_line AS l
             JOIN distribution.product AS p
               ON p.product_pk = l.product_fk
             WHERE l.customer_order_fk
                   = o.customer_order_pk))
FROM distribution.customer_order AS o
JOIN distribution.customer AS c
  ON c.customer_pk = o.customer_fk;

Where it breaks. Nothing checks the fields of a document when it is written. Suppose that a program records order SO-5013, for five GC-300 carts, and misspells quantity:

  "order_date": "2026-03-12",
  "customer": {"customer_number": "C-1009"},
  "lines": [{"line_number": 1,
             "product_number": "GC-300",

Thus, a document should copy only what must not change once it is written. A line’s unit price is such a fact: it records the price the customer was charged, which a later change of list price must not alter. A product’s description is not.

PostgreSQL’s documents are most useful beside tables, not instead of them. A table of test results, for example, can keep the columns every test has (the lot, the date, the inspector, the result) as ordinary columns with keys and constraints, and hold the measurements that differ from product to product in one JSONB column. The rules that matter are kept by the database, and the part of the record that varies is free to vary.

H.5 Choosing

Most of the data an industrial engineer designs a database for is shared by many people, obeys rules that matter, and will be asked questions no one has thought of yet. That is the data the relational model was made for, and it should be your starting point. The other kinds earn their place for particular data.

  • Records that are written and read whole, and vary in structure, such as test records, equipment configurations, or the replies of a supplier’s web service: a JSONB column in PostgreSQL, beside the columns that do not vary, or a document database if the volume calls for one.
  • Measurements at a high rate, such as sensor readings and machine states: a historian or another time-series database, with summaries loaded into a relational database for analysis.
  • A value read by key many times a second, such as a dashboard’s current state: a key-value store in front of the database that holds the facts.
  • Networks whose questions are about paths, such as a multi-tier supply network: a graph database, or a recursive query (Section 4.6) while the network is small.

A system that uses several kinds of database, each for the data it suits, is said to practice polyglot persistence (Sadalage and Fowler 2012). A plant’s information systems usually do: a historian on the floor, a relational database for orders and production, and a warehouse for analysis (Chapter 11). The skills of this book carry over to all of them, because each still has to answer the two questions of Section 2.7, and a designer who can answer them for a relational database can see how another database answers them.
