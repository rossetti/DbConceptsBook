8  Defining and Populating Tables

NoteLearning objectives

After reading this chapter you should be able to:

  • implement a relational schema as tables in a PostgreSQL database, in a script that rebuilds them from nothing
  • choose a PostgreSQL data type for each column, and avoid the types that lose or distort values
  • write CREATE TABLE statements with primary key, foreign key, unique, not-null, and check constraints
  • insert, update, and delete rows, and predict what each constraint does to a change
  • load data from a CSV file through a staging table, and check it before it enters the database
  • change a table’s definition with ALTER TABLE

The chapters so far have queried tables that already existed, and then shown where those tables come from: a class model (Chapter 5), mapped to a relational schema (Chapter 6), checked by normalization (Chapter 7). This chapter takes the last step. It turns a relational schema into tables that a database system holds, fills them with rows, and changes them as the business changes.

The statements that do this are the other half of SQL. The part of SQL that defines tables and their rules is called the data definition language (DDL): CREATE, ALTER, and DROP. The part that changes rows is called the data manipulation language (DML): INSERT, UPDATE, and DELETE, together with the SELECT of the earlier chapters. A database is built with the first and kept current with the second.

The chapter builds the distribution schema of HG Industries, stages D1 to D3, from the relational schemas of Chapter 6. It does so by reading the scripts that build the book’s own database, one clause at a time, so that every statement in the chapter is one you can run and every table is one you have already queried.

TipFollowing along

The scripts are in the companion code: code/sql/distribution/d1-customer.sql, d2-customer-order.sql, and d3-product-order-line.sql, and code/sql/load/through-d3.sql runs them all from an empty database. A query shown with its result after a change runs against a copy of the stage that is discarded afterward, so the change never reaches the book’s database; the text says which change each result assumes.

8.1 From a design to tables

This section presents the whole process of building a database from its design, before the sections that illustrate each step.

A relational schema says what tables a database holds and what rules they obey; it does not yet hold anything. Building the database from it takes five steps:

  1. Create a place for the tables. A PostgreSQL server holds databases, and a database holds schemas, each a named group of tables. HG Industries’ tables live in one database, dbconcepts in the book’s setup (Appendix A), with a schema per department.
  2. Choose a data type for each column. The type implements the column’s domain, as far as a type can; a CHECK constraint narrows it further.
  3. Create each table with its constraints. One CREATE TABLE statement per table of the relational schema declares its columns, its primary key, its alternate keys, its foreign keys with their delete rules, and its checks. A table is created after every table it refers to.
  4. Put rows into the tables. Rows are inserted by statements or loaded from files, in the same order as the tables were created, so that a foreign key always refers to a row that exists.
  5. Check the result. Queries count the rows and look for what the constraints cannot catch, as the hand check of each worked example has done.

The steps are written down as a script, a file of SQL statements run in order, rather than typed once and forgotten. A script that builds a database from nothing is its most useful description: it can be read, kept under version control beside the code that uses the database, and run again to rebuild the database on another machine or after an experiment has spoiled it. The book’s database is kept this way. code/sql/reset.sql drops its four schemas, and each file of code/sql/load/ rebuilds them through one stage. Table 8.1 says where each step is illustrated.

The first step, for the distribution department, is one statement:

CREATE SCHEMA distribution;

A table in the schema is then named with the schema in front, distribution.customer, which is how the book has written table names in every query. PostgreSQL also keeps a search path, a list of schemas it looks in for a table named without one, so that SET search_path TO distribution; lets a session write customer alone. The book’s scripts always qualify the name, so that they work whatever the search path holds.

DataGrip and DBeaver can create schemas and tables through dialogs, without a statement being typed. The dialog is a convenience, not a different mechanism: it writes a CREATE statement and sends it to the server. Both tools will show the statement, and will also generate the DDL of any existing table (DataGrip’s SQL Scripts, Generate DDL to Query Console; DBeaver’s Generate SQL, DDL), which is how you capture a database that someone built by hand as a script. The rest of this chapter writes the statements directly, since a statement can be read, kept, and run again, and a sequence of clicks cannot.

8.2 Data types

This section illustrates step 2: choosing the data type of each column.

Recall from Section 6.2 that a column’s type is chosen in two steps: first the domain is stated in words, and then an SQL type and constraints implement it (Table 6.2). A data type is the set of values a column can hold, as the database system knows it, together with the operations it allows on them. The type decides more than storage: it decides how values compare, sort, and add, and whether a value that does not belong is refused or silently changed. The book’s database uses few types, and the query below counts the columns of each across all four schemas:

Recall from Section 2.5 that the information_schema of Table 8.2 is the standard’s set of views of the catalog, the database’s description of its own tables and columns. Its type names are the standard’s long spellings: character varying is VARCHAR, and character is CHAR. The types fall into five kinds.

Whole numbers. INTEGER holds whole numbers up to about two billion, which covers every key and count in the book. SMALLINT and BIGINT hold smaller and larger ranges. The surrogate keys are INTEGER columns whose values the database generates, declared GENERATED ALWAYS AS IDENTITY, the standard form since PostgreSQL 10. Older scripts write SERIAL for the same purpose, a PostgreSQL shorthand that you will still meet.

Numbers with fractions. NUMERIC(p, s) holds exact decimal numbers with p digits in all, s of them after the decimal point: a price is NUMERIC(10,2), a measured diameter NUMERIC(10,4). The alternative, REAL or DOUBLE PRECISION, holds binary floating-point numbers, which are fast and compact but cannot represent most decimal fractions exactly. The difference is easy to show:

The :: of Table 8.3 is PostgreSQL’s shorthand for converting a value to a type, the standard’s CAST(0.1 AS DOUBLE PRECISION). The floating-point sum is not 0.3, and a comparison with 0.3 is false.

The error does not always show. PostgreSQL prints a REAL or DOUBLE PRECISION value as the shortest decimal that reads back to the same stored value, so a stored value that is not exact can print as if it were:

The REAL of Table 8.4 prints as 32.38, but the value stored is 32.380001068115234, which converting it to DOUBLE PRECISION reveals. Thus, a column of floating-point prices can look right and still not add up to the cent. For money, and for any measurement recorded to a known number of decimal places, use NUMERIC; a sum of prices that is off by a fraction of a cent fails every reconciliation. Keep floating point for quantities that are computed rather than recorded, such as the output of a simulation. PostgreSQL also has a MONEY type; avoid it, since it is PostgreSQL’s own, and how it reads and prints values depends on the server’s locale settings.

Text. VARCHAR(n) holds text of up to n characters, and refuses a longer value. CHAR(n) holds exactly n, padding a shorter value with spaces, which suits a code that always has the same length, such as a two-letter state, and little else. TEXT holds text of any length; it is PostgreSQL’s (the standard has no TEXT), and suits notes and descriptions with no natural limit. A length limit in VARCHAR(n) is a small domain rule: an order number of 40 characters is a mistake, and the limit refuses it.

A code that is written with digits is still text, and belongs in a text column. Part numbers, employee numbers, and postal codes are identifiers, not quantities: nobody adds them, and a leading zero is part of the code. Stored as a number, the zero is lost:

Dates and times. DATE holds a calendar date, TIMESTAMP a date and a time of day. The book writes date values in the ISO form '2026-01-05', which PostgreSQL reads the same way whatever its settings, and the standard’s typed literal DATE '2026-01-05', used since Section 3.2. A TIMESTAMP records a time without saying where; inspected_at is one, since HG Industries inspects in one plant. A business spread across time zones uses TIMESTAMP WITH TIME ZONE, which records an instant and displays it in the reader’s zone.

True or false. BOOLEAN holds true, false, or NULL, as the results of Table 8.3 show. The sales schema’s date dimension marks weekends with one.

A domain narrower than its type is finished with a CHECK constraint, as Section 6.2 described: list_price > 0, level BETWEEN 1 AND 3. A domain that is a short list of values, an enumeration, can be implemented in two ways (Blaha and Premerlani 1998). The list can be written into the table as a check, CHECK (unit_of_measure IN ('EA', 'FT')); or the values can be rows of a table of their own, a lookup table, which the column refers to with a foreign key. The quality schema’s defect_type table is a lookup table: each defect code is a row, with its description. The check is simpler; the lookup table lets the list grow by inserting a row instead of changing a table’s definition, and gives each value a place for its description. You should choose the lookup table when the list will change or its values need more than a name. Table 8.6 collects the choices.

Every “not” of Table 8.6 is a type that accepts the value and then misbehaves: a date stored as text sorts '10/2/2026' before '9/2/2026', and a price stored as text cannot be summed. The next section writes the types into tables.

8.3 Creating tables and constraints

This section illustrates step 3: writing a CREATE TABLE statement for each table of a relational schema, with its constraints.

Recall the complete relational schema of the customer table from Listing 6.1: five columns with their types and NULL rules, a primary key, and an alternate key. The stage D1 script turns it into one statement:

CREATE TABLE distribution.customer (
    customer_pk     INTEGER GENERATED ALWAYS AS IDENTITY
                    PRIMARY KEY,
    customer_number VARCHAR(10) NOT NULL UNIQUE,
    name            VARCHAR(60) NOT NULL,
    city            VARCHAR(40) NOT NULL,
    state           CHAR(2)     NOT NULL
);

Each line inside the parentheses declares one column: its name, its type, and its column constraints, the rules that concern that column alone. Read them against Listing 6.1. customer_pk is INTEGER, filled by the database (GENERATED ALWAYS AS IDENTITY), and the primary key (PRIMARY KEY), which also makes it NOT NULL and unique. customer_number must be present (NOT NULL) and may not repeat (UNIQUE), the alternate key. The other three columns must be present. Nothing in the listing is left out, and nothing is added.

A rule that concerns several columns is written after the columns, as a table constraint. The customer_order table of stage D2 has one, a check that compares two dates, beside a foreign key written on its column:

CREATE TABLE distribution.customer_order (
    customer_order_pk   INTEGER GENERATED ALWAYS AS IDENTITY
                        PRIMARY KEY,
    order_number        VARCHAR(10) NOT NULL UNIQUE,
    order_date          DATE        NOT NULL,
    requested_ship_date DATE,
    customer_fk         INTEGER     NOT NULL
        REFERENCES distribution.customer (customer_pk),
    CHECK (requested_ship_date >= order_date)
);

requested_ship_date has no NOT NULL, so it may be missing, as the attribute requestedShipDate [0..1] allows. customer_fk is a foreign key: REFERENCES distribution.customer (customer_pk) says that every value must be the key of an existing customer. It is written here as a column constraint, which is allowed because it concerns one column; FOREIGN KEY (customer_fk) REFERENCES distribution.customer (customer_pk) after the columns says the same thing as a table constraint, and is the only form for a foreign key of several columns. The last line is a check that involves two columns, so it is written as a table constraint. The standard requires that form for a check of several columns; PostgreSQL also accepts such a check written on one of its columns, but the table constraint is the portable form, and it says what the rule concerns.

Notice that a check passes when its condition is true or unknown. An order with no requested ship date makes requested_ship_date >= order_date unknown (Section 3.3), and the order is accepted, as it should be. A check such as this one therefore passes a NULL and does not make a column required; NOT NULL is how a column is made required. (A check written to test for NULL, such as CHECK (state IS NOT NULL), does refuse one, and NOT NULL says the same thing more plainly.)

The database gives every constraint a name, and names it in every message that reports a violation. A constraint left unnamed, as in the book’s scripts, is named by PostgreSQL from its table and columns: the check of customer_order becomes customer_order_check, the alternate key customer_order_order_number_key. A constraint can be named explicitly by writing CONSTRAINT order_ship_after_order CHECK (...), which you should do when the generated name would not tell a reader which rule was broken.

Example 8.1 (Creating the order line table) The sales department of HG Industries wants to record what each order is for: the products, the quantity of each, and the price charged, which may differ from the list price. Chapter 6 mapped the order line, composed in its order, to the complete relational schema of Listing 6.10. The example assumes stage D2, with customer_order in place, and a product table already created by the first statement of the stage D3 script.

The request. Write the CREATE TABLE statement for order_line from Listing 6.10, and confirm that the database holds every constraint the listing names.

The design. The columns come first, each line of the listing becoming one column declaration:

CREATE TABLE distribution.order_line (
    order_line_pk     INTEGER GENERATED ALWAYS AS IDENTITY
                      PRIMARY KEY,
    customer_order_fk INTEGER NOT NULL
        REFERENCES distribution.customer_order
            (customer_order_pk)
        ON DELETE CASCADE,
    line_number       INTEGER NOT NULL
                      CHECK (line_number > 0),
    product_fk        INTEGER NOT NULL
        REFERENCES distribution.product (product_pk),
    quantity          INTEGER NOT NULL
                      CHECK (quantity > 0),
    unit_price        NUMERIC(10,2) NOT NULL
                      CHECK (unit_price > 0),
    UNIQUE (customer_order_fk, line_number)
);

The two foreign keys differ in one clause. customer_order_fk adds ON DELETE CASCADE: deleting an order deletes its lines, as the composition of Section 6.3.6 requires. product_fk has no ON DELETE clause, so it takes the default, NO ACTION, and a product that has been ordered cannot be deleted. Each positive quantity, price, and line number of the listing is a CHECK on its column. The alternate key (customer_order_fk, line_number) spans two columns, so it is a table constraint, the last line.

The result. The standard view information_schema.table_constraints lists the constraints the database holds for the table:

The last condition of the query leaves out the six NOT NULL rules, which PostgreSQL’s version of the view lists as checks whose names end in not_null.

The check. Listing 6.10 names one primary key, one alternate key, two foreign keys, and three checks: seven constraints, and Table 8.7 has seven rows, one of each kind named.

Interpretation. The table now enforces the business’s rules about order lines without any program’s help. A line cannot be recorded for an order or a product that does not exist, with a zero quantity or a zero price, or with a line number its order already uses; and an order cannot be removed while leaving its lines behind.

Where it breaks. The constraints check each line alone. Nothing requires an order to have at least one line, which the multiplicity 1..* of the class model says it must; an order with no lines is accepted, and a query such as those of Section 3.7 must find it. Nor does anything tie unit_price to the product’s list_price, deliberately, since the business sells below list.

The constraints are the database’s defense, and they are worth seeing at work. A statement that breaks one is refused, with a message that names the constraint. For example, a second customer with an existing customer number breaks the alternate key:

INSERT INTO distribution.customer
    (customer_number, name, city, state)
VALUES ('C-1001', 'Riverside Supply', 'Rogers', 'AR');
ERROR:  duplicate key value violates unique constraint "customer_customer_number_key"
DETAIL:  Key (customer_number)=(C-1001) already exists.

An order line for a product that does not exist breaks a foreign key, and one with a quantity of zero breaks a check:

INSERT INTO distribution.order_line
    (customer_order_fk, line_number, product_fk,
     quantity, unit_price)
VALUES (12, 3, 9, 5, 89.00);
ERROR:  insert or update on table "order_line" violates foreign key constraint "order_line_product_fk_fkey"
DETAIL:  Key (product_fk)=(9) is not present in table "product".
INSERT INTO distribution.order_line
    (customer_order_fk, line_number, product_fk,
     quantity, unit_price)
VALUES (12, 3, 1, 0, 89.00);
ERROR:  new row for relation "order_line" violates check constraint "order_line_quantity_check"
DETAIL:  Failing row contains (23, 12, 3, 1, 0, 89.00).

Each message names the table, the constraint, and for a key the offending value, which is usually enough to find the bad row in a long script. An identity column declared GENERATED ALWAYS refuses a value supplied for it, so that the database alone numbers its rows; the message’s hint names the override that a script copying rows from another database, keys and all, would use:

INSERT INTO distribution.customer
    (customer_pk, customer_number, name, city, state)
VALUES (9, 'C-1009', 'Rogers Farm Supply', 'Rogers', 'AR');
ERROR:  cannot insert a non-DEFAULT value into column "customer_pk"
DETAIL:  Column "customer_pk" is an identity column defined as GENERATED ALWAYS.
HINT:  Use OVERRIDING SYSTEM VALUE to override.

The order of the statements in a script follows from the foreign keys. A table can be created only after every table it refers to, so the stage scripts create customer, then customer_order, then product and order_line. Removing tables runs the other way: DROP TABLE removes a table and its rows, and it refuses to remove a table that another table refers to:

DROP TABLE distribution.customer;
ERROR:  cannot drop table distribution.customer because other objects depend on it
DETAIL:  constraint customer_order_customer_fk_fkey on table distribution.customer_order depends on table distribution.customer
HINT:  Use DROP ... CASCADE to drop the dependent objects too.

As the message’s hint says, DROP TABLE distribution.customer CASCADE would remove the foreign key constraints that depend on customer and then the table; the tables that referred to it would remain, without their foreign keys. DROP SCHEMA distribution CASCADE, which code/sql/reset.sql runs, removes the schema with every table in it. Once kept, neither can be undone, and you should keep them in scripts that rebuild what they remove. (A change can be tried without being kept, inside a transaction, as Section 8.4 shows.) The tables now exist, and the next section changes their rows.

8.4 Inserting, updating, and deleting rows

This section illustrates step 4: putting rows into tables, and then changing and removing them as the business changes.

INSERT adds rows to a table. Its usual form names the table, lists the columns it supplies, and gives a row of values for each row to add, in the same order as the columns:

INSERT INTO distribution.customer
    (customer_number, name, city, state)
VALUES ('C-1009', 'Rogers Farm Supply', 'Rogers', 'AR'),
       ('C-1029', 'Crowley''s Ridge Hardware',
        'Jonesboro', 'AR');

The statement adds two customers. A column left out of the list, such as customer_pk, takes its default: the next identity value for a key, and NULL for a column with no default. You should always write the column list. Without it, the values are matched to the table’s columns in the order the table declared them, and a script written that way breaks, or worse loads values into the wrong columns, when a column is added. Notice the second name: a quote inside a text value is written twice, 'Crowley''s Ridge Hardware', which is how SQL tells the quote in the value from the quote that ends it.

TipTrying a change without keeping it

DataGrip and DBeaver keep each statement’s change the moment it runs (auto-commit). A change run that way alters your copy of the stage for good, and the examples and exercises that assume the stage as loaded no longer give the book’s results. To try a change without keeping it, run BEGIN before it and ROLLBACK after it:

BEGIN;
INSERT INTO distribution.customer
    (customer_number, name, city, state)
VALUES ('C-1009', 'Rogers Farm Supply', 'Rogers', 'AR');
SELECT * FROM distribution.customer;
ROLLBACK;

The statements between the two form a transaction, and ROLLBACK discards everything it changed, as if it had never run. After a statement is refused, PostgreSQL refuses every later statement of the transaction until the ROLLBACK, so try each change that may be refused in a transaction of its own. Chapter 9 presents transactions. Try the insert above, and every change of this chapter’s examples and exercises, this way: Example 8.2 and Example 8.3 assume stage D3 as loaded, and both add C-1009 themselves. A change kept by mistake is undone by reloading the stage with its script in code/sql/load/.

A foreign key column needs the key of the row it refers to, and a generated key is not something you know in advance. The stage scripts can write the keys as numbers, since they insert into empty tables in a fixed order (code/sql/README.md explains). A statement that records a new order for an existing customer instead looks the key up by the customer’s number, with a scalar subquery (Section 3.8) in place of the value. The example below records a whole order this way.

Example 8.2 (Recording a new customer’s first order) On April 2, 2026, Rogers Farm Supply of Rogers, Arkansas, placed its first order with HG Industries: eight GC-300 steel garden carts at $119.00, twelve HT-100 hand trucks at $89.00, and ten HT-200 convertible hand trucks at $139.00, to ship by April 9. The sales department gave it customer number C-1009 and the order the number SO-5018. The example assumes stage D3.

The request. Record the customer, the order, and its three lines, referring to the customer and the products by their business numbers.

The design. The customer comes first, since the order refers to it:

INSERT INTO distribution.customer
    (customer_number, name, city, state)
VALUES ('C-1009', 'Rogers Farm Supply', 'Rogers', 'AR');

The order’s customer_fk is found by a subquery on customer_number:

INSERT INTO distribution.customer_order
    (order_number, order_date, requested_ship_date,
     customer_fk)
VALUES ('SO-5018', DATE '2026-04-02', DATE '2026-04-09',
        (SELECT customer_pk
         FROM distribution.customer
         WHERE customer_number = 'C-1009'));

Each line looks up its order by order_number and its product by product_number in the same way:

INSERT INTO distribution.order_line
    (customer_order_fk, line_number, product_fk,
     quantity, unit_price)
VALUES
  ((SELECT customer_order_pk
    FROM distribution.customer_order
    WHERE order_number = 'SO-5018'), 1,
   (SELECT product_pk FROM distribution.product
    WHERE product_number = 'GC-300'), 8, 119.00),
  ((SELECT customer_order_pk
    FROM distribution.customer_order
    WHERE order_number = 'SO-5018'), 2,
   (SELECT product_pk FROM distribution.product
    WHERE product_number = 'HT-100'), 12, 89.00),
  ((SELECT customer_order_pk
    FROM distribution.customer_order
    WHERE order_number = 'SO-5018'), 3,
   (SELECT product_pk FROM distribution.product
    WHERE product_number = 'HT-200'), 10, 139.00);

The result. After the three statements, a query joins the new rows back together:

The check. A generated key comes from the column’s identity counter, not from a count of the rows. On a freshly loaded stage D3 the counters of customer and customer_order stand at 8 and 12, the last keys the load used, so the new customer’s key is 9 and the new order’s is 13, as Table 8.8 shows. An insert takes the next value even when it is refused or rolled back, and the value is never given back; in a copy of the stage where inserts have been tried, the keys are higher and the rows are otherwise the same. The three line values are 8 × 119.00 = 952.00, 12 × 89.00 = 1,068.00, and 10 × 139.00 = 1,390.00, and the order is worth $3,410.00.

Interpretation. Rogers Farm Supply is now a customer with one open order, and every query of the earlier chapters counts it: it appears in the order report, in the sales of each product, and among the orders due to ship on April 9.

Where it breaks. A subquery that finds no row returns NULL. A mistyped product number, 'HT-210', makes product_fk NULL, and the NOT NULL of the column refuses the line:

INSERT INTO distribution.order_line
    (customer_order_fk, line_number, product_fk,
     quantity, unit_price)
VALUES
  ((SELECT customer_order_pk
    FROM distribution.customer_order
    WHERE order_number = 'SO-5018'), 3,
   (SELECT product_pk FROM distribution.product
    WHERE product_number = 'HT-210'), 10, 139.00);
ERROR:  null value in column "product_fk" of relation "order_line" violates not-null constraint
DETAIL:  Failing row contains (23, 13, 3, null, 10, 139.00).

The refusal protects the order. Had product_fk allowed NULL, the line would have been recorded for no product at all.

INSERT can also take its rows from a query, INSERT INTO t (columns) SELECT ..., which adds every row the query returns. It is the form used to copy or transform rows already in the database, and Section 8.5 uses it to move loaded rows into their table. It has one danger the VALUES form lacks: a query that finds no rows inserts nothing, and reports success.

UPDATE changes values in existing rows. It names the table, sets one or more columns to new values, and chooses the rows with a WHERE clause, as a query does. Suppose that HG Industries raises the list prices of its garden carts by 5 percent, rounded to the cent. Before changing anything, preview the change with a query that selects the same rows and computes the new values:

Table 8.9 shows the two rows the update will touch and what they will become. The update itself reuses the preview’s WHERE clause and its expression:

UPDATE distribution.product
SET list_price = ROUND(list_price * 1.05, 2)
WHERE product_number LIKE 'GC-%';

The two carts in Table 8.10 have the prices the preview promised, $124.95 and $156.45, and the hand trucks are unchanged. The preview is a habit worth keeping. An UPDATE without a WHERE clause changes every row of the table, and the database will not ask whether you meant it; the preview shows the rows before they change. Notice also that the new prices apply to future orders only. The lines already recorded keep their unit_price, which is why Section 7.6 kept the price of a line apart from the product’s.

An update must leave every row within its constraints, or it is refused as an insert would be. Moving an order’s requested ship date before its order date breaks the check of customer_order:

UPDATE distribution.customer_order
SET requested_ship_date = DATE '2026-01-01'
WHERE order_number = 'SO-5001';
ERROR:  new row for relation "customer_order" violates check constraint "customer_order_check"
DETAIL:  Failing row contains (1, SO-5001, 2026-01-05, 2026-01-01, 1).

DELETE removes rows, chosen by a WHERE clause. The foreign keys decide what happens to the rows that refer to them. Recall from Section 6.3.6 that an order line is composed in its order, so that deleting an order deletes its lines; Chapter 6 promised to show it, at stage D5, with order SO-5012, which has two lines and has not shipped. Before the deletion, the last two orders have these lines:

The deletion names only the order:

DELETE FROM distribution.customer_order
WHERE order_number = 'SO-5012';

Stage D5 holds 22 order lines, and Table 8.12 shows 20, none of them SO-5012’s: the database deleted the two lines itself, because of the ON DELETE CASCADE of customer_order_fk. (FILTER limits one aggregate to some rows; it is standard SQL, and PostgreSQL supports it.) A foreign key without the cascade refuses instead. Order SO-5001 has shipped, and its shipment refers to it:

DELETE FROM distribution.customer_order
WHERE order_number = 'SO-5001';
ERROR:  update or delete on table "customer_order" violates foreign key constraint "shipment_customer_order_fk_fkey" on table "shipment"
DETAIL:  Key (customer_order_pk)=(1) is still referenced from table "shipment".

The refusal is the design working. The shipment is a record of goods that left the warehouse, and the database will not let the order it fulfilled disappear from under it. In the same way, a product that has been ordered cannot be deleted, since order lines refer to it:

DELETE FROM distribution.product
WHERE product_number = 'HT-100';
ERROR:  update or delete on table "product" violates foreign key constraint "order_line_product_fk_fkey" on table "order_line"
DETAIL:  Key (product_pk)=(1) is still referenced from table "order_line".

A DELETE without a WHERE clause removes every row and keeps the table. TRUNCATE, standard since SQL:2008, also empties a table, faster, without examining the rows one at a time, but it is not the same. A DELETE follows each foreign key’s delete rule, so at stage D3 deleting every order deletes every order line with it; TRUNCATE refuses a table that another table refers to, unless the tables that refer to it are truncated with it:

TRUNCATE distribution.customer_order;
ERROR:  cannot truncate a table referenced in a foreign key constraint
DETAIL:  Table "order_line" references "customer_order".
HINT:  Truncate table "order_line" at the same time, or use TRUNCATE ... CASCADE.

Neither statement removes the table; DROP TABLE does (Section 8.3). The three are easy to confuse, and they differ in what remains: rows and table, table only, or nothing.

Under auto-commit, each statement of this section changes the database as soon as it runs, and each is complete in itself; inside a BEGIN and ROLLBACK, as in the callout of Section 8.4, its change is not kept. Chapter 9 shows how several statements, such as the three inserts of Example 8.2, can be made to succeed or fail together. The next section adds rows in bulk, from files.

8.5 Loading data from files

This section illustrates step 4 again, for rows that arrive as files, and step 5, checking them before they enter the database.

Data often reaches a database as a file. A colleague exports a list from another system or a spreadsheet, and the rows must be loaded into tables that someone else designed. The usual form is a CSV file (comma-separated values): plain text, one row per line, the values separated by commas, and usually a first line of column names. A value that contains a comma or a quote is enclosed in double quotes. The file carries no types, no keys, and no rules; everything in it is text, and nothing in it has been checked.

PostgreSQL offers two ways to load such a file, and the tools add a third:

  • COPY table FROM 'file' is an SQL statement that the server runs. It reads a file on the server’s own machine, so it needs a server-side path, and PostgreSQL allows it only to superusers and to roles granted pg_read_server_files.
  • \copy table FROM 'file' is a psql command (Appendix A) that reads a file on your machine and sends its rows to the server. It takes the same options as COPY, needs no special privilege, and is the form the book uses.
  • The import wizards of DataGrip and DBeaver read a file on your machine, show its first rows, and map its columns to a table’s columns. They are convenient for a single load, and they do what \copy does.

Whichever you use, do not load a file straight into its final table. If one row breaks a constraint, the whole load is refused, and you learn only about the first bad row; and a value that is wrong but legal, such as a city misspelled, goes in unnoticed. Load the file instead into a staging table, a table with the file’s columns, all of type TEXT and without constraints, which accepts anything. Then examine the staged rows with queries, and move them into the real table with INSERT ... SELECT, cleaning them on the way.

Example 8.3 (Loading new customers from a file) HG Industries is expanding into Oklahoma, Kansas, and Texas, and the sales department has signed 22 new customers. A sales assistant exported them from the contact list to code/data/new-customers-raw.csv, one customer per line with a header line: the customer number, name, city, and state. The first lines of the file are:

A code written with digits loses its leading zeros if the file passed through a spreadsheet that took the code for a number (Table 8.5), and nothing in the database can restore them. Dates arrive in more than one form: 2026-04-13 and 4/13/2026 are the same day, and a staging query must find which form each row uses before converting it, as Exercise 8.8 asks. 8.6 Changing a table’s definition

This section changes the definition of tables that already hold rows.

A design changes after the database is built: the business records something new, a rule is discovered, or two departments’ data must be connected. Dropping and recreating a table would lose its rows, so SQL changes a table in place with ALTER TABLE. Table 8.17 lists the changes the book uses.

A change must hold for the rows already there, and the database checks them before it accepts the change. Requiring a requested ship date on every order is refused at stage D3, since two orders have none:

ALTER TABLE distribution.customer_order
    ALTER COLUMN requested_ship_date SET NOT NULL;
ERROR:  column "requested_ship_date" of relation "customer_order" contains null values

A constraint added to a table applies to every later change. The customer load of Example 8.3 repaired a lower-case state in its INSERT ... SELECT; a check makes the database refuse one. Its name is chosen so that a message names the rule:

ALTER TABLE distribution.customer
    ADD CONSTRAINT customer_state_in_capitals
    CHECK (state = UPPER(state));
INSERT INTO distribution.customer
    (customer_number, name, city, state)
VALUES ('C-1017', 'Canadian River Home Center',
        'Norman', 'ok');
ERROR:  new row for relation "customer" violates check constraint "customer_state_in_capitals"
DETAIL:  Failing row contains (9, C-1017, Canadian River Home Center, Norman, ok).

The most common change adds a column to connect data that were designed apart. Stage P1 adds the production department’s parts, and each product that distribution sells is a manufactured part: the HT-100 hand truck is part HT-100. The P1 script, code/sql/production/p1-part.sql, connects them in three steps, which is the pattern for adding a required column to a table that already has rows. First, the column is added, allowing NULL, since the existing products have no value for it yet:

ALTER TABLE distribution.product
    ADD COLUMN manufactured_part_fk INTEGER
        REFERENCES production.manufactured_part (part_fk);

Second, an UPDATE fills it for every product, finding each product’s part by its number. The standard form sets the column to a correlated subquery (Section 3.8):

UPDATE distribution.product
SET manufactured_part_fk =
    (SELECT part_pk
     FROM production.part
     WHERE part.part_number = product.product_number);

The P1 script writes the same update in PostgreSQL’s own form, UPDATE ... FROM production.part WHERE ..., which joins the table being updated to another; both give the same result here. Third, once every product has its part, the column is required:

ALTER TABLE distribution.product
    ALTER COLUMN manufactured_part_fk SET NOT NULL;

The stage P1 database holds the result, and a join through the new column finds each product’s part:

Each product of Table 8.18 has found the part with its own number, so the update matched all four. Had one product had no part of the same number, its column would have stayed NULL, and the third step would have been refused, as the ship-date change was: the order of the three steps turns a silent gap into a refusal. The same pattern, create bare, fill, then constrain, is how a large load is often done: the tables are created without their keys, loaded, and the keys added with ALTER TABLE ... ADD CONSTRAINT, so that each constraint checks all the rows once.

A change made with ALTER TABLE must also be made to the scripts that build the database, or the next rebuild will lose it. The book’s database does this by adding each change as a stage script that runs after the scripts before it, as p1-part.sql runs after the distribution stages. You should keep your own databases the same way: the scripts, not the running database, are the definition.

8.7 Summary

A database is built from its relational schema by a script. The script creates a schema, then each table after the tables it refers to, then the rows in the same order; kept and run again, it is the database’s most useful description.

A data type implements a domain, and the wrong type distorts values. Use INTEGER for keys and counts, NUMERIC for money and recorded measurements, text for every code even one written in digits, and DATE or TIMESTAMP for dates. Floating point cannot hold most decimal fractions exactly, and a number drops a code’s leading zero.

Constraints make the database enforce the business’s rules. PRIMARY KEY, UNIQUE, NOT NULL, REFERENCES, and CHECK implement a relational schema’s keys, NULL rules, foreign keys, and domains, and a statement that breaks one is refused with a message naming it. A rule about one column can be a column constraint; a rule about several is a table constraint, as the standard requires (PostgreSQL also accepts a check of several columns on one column).

INSERT, UPDATE, and DELETE change rows, and the constraints judge every change. Write the column list of every INSERT, look up a generated key by its business number with a subquery, and preview every UPDATE and DELETE with a query that selects the same rows. A foreign key decides what a deletion does to the rows that refer to it: ON DELETE CASCADE deletes them with it, and the default refuses the deletion.

A file is loaded into a staging table, examined, and then moved. Load it with psql’s \copy or a tool’s import wizard into a table of text columns with no constraints; find duplicates, malformed values, and existing keys with queries; and move the rows with an INSERT ... SELECT that repairs what the queries found. Count the rows at each step.

ALTER TABLE changes a table that holds rows, and the rows must satisfy the change. A new required column is added in three steps: add it allowing NULL, fill it with an UPDATE, and then require it. Every change to a running database belongs in the scripts that rebuild it.
